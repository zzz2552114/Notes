 好消息：这个盘正好是"最安全"的情况（我直接读了 VHDX 里的分区表确认）

 从你 D:\hyper-V\ubuntu24\ 的磁盘文件里解析出的真实布局：

 ┌──────┬───────────────────────┬──────────┬────────────────────────────┐
 │ 分区 │ 起止                  │ 大小     │ 类型                       │
 ├──────┼───────────────────────┼──────────┼────────────────────────────┤
 │ p14  │ LBA 2048–10239        │ 4 MiB    │ BIOS boot                  │
 ├──────┼───────────────────────┼──────────┼────────────────────────────┤
 │ p15  │ LBA 10240–227327      │ 106 MiB  │ EFI 系统分区 (ESP)         │
 ├──────┼───────────────────────┼──────────┼────────────────────────────┤
 │ p1   │ LBA 227328 – 25165790 │ 11.9 GiB │ Linux 文件系统（= 你的 /） │
 └──────┴───────────────────────┴──────────┴────────────────────────────┘

 - 磁盘虚拟容量 = 12.00 GiB，文件 9.46GB → 动态扩展 VHDX；
 - root(p1) 正好是磁盘上最后一个分区，结束位置就是磁盘最后一个可用扇区；
 - 所以扩大磁盘后，新空间紧跟在 root 后面 → 只需要"把 p1 往后延伸 + 扩展文件系统"，不需要移动/重建/删除任何分区，也完全
   不碰 ESP 和引导。

 这就是"最安全最简便"的路线，5~10 分钟搞定，不用重装、不用重启进救援模式。

 ────────────────────────────────────────────────────────────────────────────────

 步骤 1：关机

 ```bash
   sudo poweroff          # 在 Ubuntu 里执行；或在 Hyper-V 管理器里右键 → 关闭
 ```

 等状态变成 "关闭"。

 │ （可选但推荐，不放心就做）关机后把 D:\hyper-V\ubuntu24\ 整个文件夹复制一份到 D:\hyper-V\ubuntu24-backup\（约
 │ 9.5GB，D 盘还有 107GB 空余），出问题可以整体回滚。

 步骤 2：删除检查点 ⚠️ 必须做

 有检查点时（存在 .avhdx 差分层）无法扩展父盘 —— 这是你唯一的"拦路虎"。
 （代价：会丢掉今天那个检查点/8GB 内存快照；你的数据没影响，用户文档/代码都在系统盘里，不受此操作影响。）

 GUI：Hyper-V 管理器 → 选中 Ubuntu24 → 下方「检查点」面板 → 右键那个检查点 → 删除检查点 → 等合并完成。

 或管理员 PowerShell（不用手打中文名字）：

 ```powershell
   Get-VMSnapshot -VMName Ubuntu24 | ft Name,SnapshotType
   Get-VMSnapshot -VMName Ubuntu24 | Remove-VMSnapshot
   Get-VMHardDiskDrive -VMName Ubuntu24          # 确认路径已回到 livecd...vhdx，不再指向 .avhdx
 ```

 步骤 3：扩展虚拟磁盘到 40GB

 GUI（最直观）：设置 → SCSI 控制器 → 那块硬盘 → 编辑 → 下一步 → 扩展 → 新大小 40960 MB → 完成 → 确定。

 或 管理员 PowerShell：

 ```powershell
   Resize-VHD -Path 'D:\hyper-V\ubuntu24\livecd.ubuntu-desktop-hyperv.vhdx' -SizeBytes 40GB
   Get-VHD  -Path 'D:\hyper-V\ubuntu24\livecd.ubuntu-desktop-hyperv.vhdx' | ft VhdType,FileSize,Size
 ```

 │ 动态 VHDX 的好处：虚拟容量变 40GB，但宿主机文件现在还是 ~9.5GB，用多少长多少。

 步骤 4：启动虚拟机，然后在 Ubuntu 里扩文件系统（在线操作，不用重启）

 ```bash
   lsblk                     # 应看到 sda 变成 40G，而 sda1 还是 12G  ← 正常
   sudo growpart /dev/sda 1  # 把 p1 延伸到磁盘末尾
   sudo resize2fs /dev/sda1  # 把 ext4 文件系统扩满
   df -h /                   # 期望：约 39G，已用 ~9G
 ```

 - growpart 这个工具镜像里已经装好（包 cloud-guest-utils，我核对过它的包清单）；万一提示找不到：sudo apt install -y
   cloud-guest-utils。
 - root 是挂载中使用的情况 growpart/resize2fs 都支持在线扩容，所以不需要救援模式、不需要 umount。
 - 万一 growpart 报错（极少见），用 parted 兜底：
   ```bash
     sudo parted /dev/sda ---pretend-input-tty resizepart 1 100%
     sudo resize2fs /dev/sda1
   ```

 步骤 5：收尾

 1. df -h / 确认 ~39G；
 2. 关机状态下拍一个新检查点（只有差分层，几乎不占空间），命名如 40G-扩容完成；
 3. 以后空间不够时，重复步骤 1→5 即可（唯一要记住的：扩展前必须先删掉检查点）。

 ────────────────────────────────────────────────────────────────────────────────

 要不要换成"加一块新盘"？（不建议，但你该知道）

 更保守的做法是：不动原盘，Hyper-V 里新增一块 20GB 的 VHDX，在系统里格式化成 ext4，挂到 /home 或 /data。
 - 优点：零风险（完全不碰现有分区）。
 - 缺点：root 还是只有 12G —— 而 clang/cmake/doxygen（约 2~3GB）装在 /usr，/var/lib/docker、/var/lib/postgresql 也在
   root 上，早晚还是会爆；把 /home 搬过去也是个额外操作。
 - 你的情况 p1 是最后一个分区 → 直接扩容更省事、也同样是"只向前延伸"，所以走上面的主方案。

 ────────────────────────────────────────────────────────────────────────────────
