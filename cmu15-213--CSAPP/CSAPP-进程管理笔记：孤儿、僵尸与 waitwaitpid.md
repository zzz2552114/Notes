# 进程管理笔记：孤儿、僵尸与 wait/waitpid

## 1. 孤儿进程（Orphan Process）
**场景**：父进程先退出了（比如执行了 `exit(0)`），但子进程还在跑。

*   **会发生什么？**
    子进程会变成“孤儿”，被系统的 `init` 进程（PID 1）或 `systemd` 收养。它会一直留在系统里，直到运行结束或者被人手动 `kill` 掉。
*   **init 为什么不直接杀死它？**
    因为操作系统认为进程是独立的生命周期。父进程死了，子进程可能还有自己的任务没做完（比如后台 Web 服务、守护进程 Daemon 的雏形就是这样）。`init` 的角色是“孤儿院院长”，只负责收留和善后，不负责随意处决。只要它不退出，就会一直占着 CPU 和内存。
*   **⚠️ 注意死循环**
    如果子进程写了个 `while(1);` 这种死循环，父进程又退出了，那它就会变成孤儿并且疯狂吃满一个 CPU 核心，必须手动 `kill -9` 解决。

## 2. 僵尸进程（Zombie Process）
**场景**：子进程先退出了，但父进程还在跑，且**没有调用 wait() 给它收尸**。

*   **状态**：子进程的代码和数据已经被释放，但内核里的 PCB（进程控制块）还在，状态为 `Z`。用 `kill -9` 杀不死它，因为它已经死了。
*   **父进程退出会怎样？**
    如果父进程一直不调用 `wait()` 收尸，僵尸进程就会一直占着进程号（PID）。**但是**，如果父进程最终退出了，这个僵尸就会变成“孤儿僵尸”，被 `init` 接管。`init` 会非常尽职地立刻调用 `wait()` 把它彻底回收（清理掉进程表里的残留）。
*   **💡 容器环境的坑**
    在 Docker 里，如果 PID 1 是你的 Node.js 或 Python 程序（而不是标准的 `init`），它必须自己负责调用 `wait()` 回收子进程，否则容器里的僵尸进程会越积越多，最后把 PID 耗尽。

---

## 3. wait()：给子进程收尸
**核心作用**：父进程调用 `wait()` 来同步和回收子进程，防止僵尸进程产生。

*   **行为**：
    *   父进程会**挂起（阻塞）**，直到它的**任意一个**子进程退出。
    *   返回值是那个退出的子进程 PID。
    *   如果传入 `child_status` 指针，内核会把子进程的退出信息写进去。
*   **如何解析状态？**
    必须用 `<sys/wait.h>` 里的宏来解析：
    *   `WIFEXITED(status)`：判断是否正常退出。如果是，用 `WEXITSTATUS(status)` 拿具体的退出码（比如 `exit(100+i)` 里的数字）。
    *   `WIFSIGNALED(status)` / `WTERMSIG(status)`：判断是否被信号杀死，并拿到信号编号。

## 4. waitpid()：精准定位某个子进程
**核心作用**：`wait()` 是盲盒（谁先死等谁），`waitpid()` 则是精准点名。

*   **函数原型**：`pid_t waitpid(pid_t pid, int *status, int options)`
*   **行为**：挂起当前进程，直到**指定的那个 PID** 的子进程退出。
*   **实际应用场景**（结合课件代码）：
    如果父进程 `fork` 了 N 个子进程并存进数组，为了拿到每一个子进程对应的退出状态，父进程通常会用一个 `for` 循环，从 `N-1` 到 `0` 倒序调用 `waitpid(pid[i], ...)`。这样就实现了**等待所有子进程，但按特定顺序收尸**。
*   **进阶用法**：第三个参数 `options` 可以传入 `WNOHANG`，变成非阻塞模式。父进程可以先看看子进程死没死，没死就先去干别的事，这在写高性能服务器时很重要。

---

**一句话总结**：
父进程生完孩子必须负责（或者让别人负责）。要么用 `wait()` 批量收尸，要么用 `waitpid()` 精准收尸。否则，要么留下疯狂吃 CPU 的孤儿，要么留下占着茅坑不拉屎的僵尸。
