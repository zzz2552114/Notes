# Unix 内核中打开文件的三张表详解

这张图是操作系统/系统编程中最经典的一张图，讲的是 Unix 内核如何用**三层间接结构**来表示一个进程打开的文件。下面我逐字逐句、从左到右拆开讲。

------

## 一、图的标题与说明文字

### 标题：How the Unix Kernel Represents Open Files

"Unix 内核如何表示打开的文件"。核心思想是：**一个打开的文件不是用一个结构体直接表示的，而是用三张表通过指针串联起来**。这种分层设计是为了在"每个进程独立"和"全局共享"之间做权衡。

### 说明文字：Two descriptors referencing two distinct open files.

"两个描述符引用两个不同的打开文件"。这是本图的场景设定：当前进程里有两个文件描述符（fd 1 和 fd 4），它们分别指向两个**不同的**打开文件实例。

### Descriptor 1 (stdout) points to terminal, and descriptor 4 points to open disk file

"描述符 1（标准输出 stdout）指向终端，描述符 4 指向一个打开的磁盘文件"。

- fd 1 是标准输出，通常绑定到终端设备（tty）。
- fd 4 是程序中通过 `open()` 打开的一个普通磁盘文件。
- 注意 fd 0、fd 2、fd 3 在图中也画了格子但没有连线，表示它们可能未使用或本图不关注。

------

## 二、第一张表：Descriptor Table（描述符表）

### 标注：`[one table per process]`

**每个进程有且仅有一张**，是进程私有的。

### 它是什么

描述符表本质上是一个**数组**（在 Linux 中是 `struct fdtable`，里面核心是一个 `struct file __rcu **fd` 指针数组）。数组的**下标**就是文件描述符（fd 0, 1, 2, 3, 4...），数组的**每个元素**是一个指针，指向 Open File Table 中的某一项。

### 图中内容逐行解释

| 左边标注 | fd 编号 | 含义                                    |
| -------- | ------- | --------------------------------------- |
| stdin    | fd 0    | 标准输入，图中未画连线                  |
| stdout   | fd 1    | 标准输出，箭头指向 File A（terminal）   |
| stderr   | fd 2    | 标准错误，图中未画连线                  |
| —        | fd 3    | 未使用/未关注                           |
| —        | fd 4    | 程序打开的文件，箭头指向 File B（disk） |

### 它的作用

1. **提供轻量级句柄**：用户程序不需要直接操作内核中的复杂文件对象，只需要传一个整数（fd）给系统调用（`read`、`write`、`close`），内核用这个整数去描述符表里查指针。
2. **进程隔离**：因为每个进程有自己的描述符表，所以进程 A 的 fd 4 和进程 B 的 fd 4 可以完全指向不同的东西，互不干扰。
3. **支持重定向**：修改描述符表里某个下标的指针，就实现了 shell 的 `>`、`<`、`2>&1` 等重定向。
4. **close-on-exec 标志**：每个描述符表项还携带 `FD_CLOEXEC` 等标志，控制 `exec` 时是否自动关闭该 fd。

------

## 三、第二张表：Open File Table（打开文件表）

### 标注：`[shared by all processes]`

**由所有进程共享**，是内核中的全局表（在 Linux 中没有一个叫"open file table"的全局数组，而是每个打开的文件对应一个 `struct file` 对象，通过引用计数管理；但教学上统一称为 open file table）。

### 它是什么

每调用一次 `open()`，内核就创建一个 `struct file`（即图中的一个 File A / File B 方框），并把它挂到这张表里。描述符表中的指针指向的就是这个 `struct file`。

### 图中字段逐字解释

以 **File A (terminal)** 为例：

- **File pos**（文件偏移量 / current file offset）：记录当前读写位置。`read()`/`write()` 会推进这个值，`lseek()` 可以直接修改它。图底部特意用蓝色字强调：**File pos is maintained per open file**——文件偏移量是按"每次打开"维护的，不是按文件本身维护的。这是理解后续 fork 行为的关键。
- **refcnt=1**（引用计数）：当前有多少个描述符表项指向这个 `struct file`。图中 File A 只有 fd 1 指向它，所以 refcnt=1。如果 `dup()` 或 `fork()` 后，这个计数会增加。
- **`...`**：还有其他字段，例如文件状态标志（`O_RDONLY`、`O_APPEND`、`O_NONBLOCK` 等）、指向 v-node 的指针、文件操作函数表（`f_op`）等。

**File B (disk)** 结构完全一样，只是它代表的是磁盘文件而不是终端。

### 它的作用

1. **保存"打开状态"**：同一个磁盘文件被打开两次（两次 `open`），会产生两个不同的 `struct file`，各自有独立的 `file pos` 和独立的打开标志。这就是为什么图中强调 "per open file"。
2. **引用计数管理生命周期**：当 `close()` 一个 fd 时，只是把对应 `struct file` 的 refcnt 减 1；只有减到 0 时，内核才真正销毁这个 `struct file`。
3. **解耦描述符与文件元数据**：`struct file` 不直接存文件大小、权限等静态信息，而是通过指针指向 v-node，让多个打开实例可以共享同一份元数据。

------

## 四、第三张表：v-node Table（v 节点表）

### 标注：`[shared by all processes]`

**由所有进程共享**，也是内核全局表。

### 它是什么

v-node（virtual node，虚拟节点）是对"一个文件本身"的抽象，与"是否被打开"无关。无论这个文件有没有被进程打开，它在文件系统中都对应一个 v-node（在 Linux 中实际是 `struct inode`，v-node 是 BSD/教学术语，概念等价）。

### 图中字段逐字解释

右边大括号标注 **Info in stat struct**，意思是这些字段正是 `stat()` 系统调用返回的 `struct stat` 里的信息：

- **File access**：文件访问权限（rwxr-xr-x 等，即 `st_mode` 的权限位）。
- **File size**：文件大小（字节数，`st_size`）。
- **File type**：文件类型（普通文件、目录、字符设备、块设备、符号链接等，也在 `st_mode` 中）。
- **`...`**：还有 inode 编号、所有者 uid/gid、时间戳（atime/mtime/ctime）、硬链接数、指向具体文件系统操作函数的指针等。

### 它的作用

1. **存储文件的静态元数据**：这些信息属于文件本身，不随"打开方式"或"读写位置"变化，所以所有打开实例共享一份即可，避免冗余。
2. **抽象不同文件系统**：v-node 是统一接口，下层可以是 ext4、NTFS、NFS、procfs 等，v-node 屏蔽了具体文件系统的差异。
3. **与打开状态解耦**：一个 v-node 可以被多个 `struct file` 指向（同一个文件被多次打开），也可以没有任何 `struct file` 指向（文件存在但当前没被打开）。

------

## 五、三张表的整体串联逻辑

以 fd 1 为例，完整的指针链是：

```
进程的 fd 1 (描述符表下标1)
    ↓ 指针
Open File Table 中的 File A (struct file)
    ↓ 指针
v-node Table 中的 terminal 设备节点 (struct inode/vnode)
```

以 fd 4 为例：

```
进程的 fd 4 (描述符表下标4)
    ↓ 指针
Open File Table 中的 File B (struct file)
    ↓ 指针
v-node Table 中的磁盘文件节点 (struct inode/vnode)
```

**为什么要分三层？** 一句话总结：

- **描述符表**解决"每个进程自己的句柄和重定向"问题；
- **打开文件表**解决"每次打开的独立状态（偏移量、打开标志）"问题；
- **v-node 表**解决"文件本身的元数据全局唯一"问题。

------

## 六、fork 之后：父进程与子进程共用哪些、拷贝哪些

这是这张图最核心的考点。`fork()` 创建子进程时，内核会复制进程的资源，但三张表的处理方式**各不相同**。

### 1. Descriptor Table —— 完全拷贝（子进程独立拥有一份）

`fork()` 时，子进程会获得父进程描述符表的**一份完整拷贝**（在 Linux 中是 `copy_files()` 完成，复制 `struct files_struct`，其中包含 fd 数组）。

- 子进程有自己独立的描述符表，fd 编号与父进程一一对应。
- 父进程 fd 1 指向什么，子进程 fd 1 也指向什么（指针值相同）。
- **但是**，子进程之后对自己描述符表的修改（比如 `close(fd)`、`dup2()`、重新 `open` 覆盖某个 fd）**不会影响**父进程，反之亦然。因为这是两份独立的数组。

> 类比：像两个人各自拿着一张写满地址的纸条，纸条内容一开始完全一样，但其中一个人涂改自己纸条上的地址，不影响另一个人的纸条。

### 2. Open File Table —— 共用（不拷贝，refcnt +1）

子进程描述符表里拷贝过来的指针，**直接指向父进程正在使用的同一个 `struct file`**。内核不会为子进程创建新的 `struct file`，只是把对应 `struct file` 的 `refcnt` 加 1。

这意味着：

- **父子进程共享文件偏移量（file pos）**。父进程 `write` 推进了偏移量，子进程接下来 `read` 会从新位置开始，反之亦然。这是最容易出 bug 的地方。
- **父子进程共享文件状态标志**（如 `O_APPEND`、`O_NONBLOCK`）。
- 只有当父子进程都 `close` 了对应的 fd（refcnt 减到 0），这个 `struct file` 才会被销毁。

> 图中原本 refcnt=1，fork 之后对应项的 refcnt 变成 2。

### 3. v-node Table —— 共用（本来就是全局的，无所谓拷贝）

v-node 是内核全局表，代表文件本身，与进程无关。父子进程通过同一个 `struct file` 自然指向同一个 v-node。即使不通过同一个 `struct file`（比如父子各自独立 `open` 同一个文件），最终也指向同一个 v-node。

- 文件大小、权限、类型等元数据天然全局共享。
- 不存在"拷贝 v-node"的说法。

------

## 七、总结对照表

| 资源                                | fork 后的行为                | 原因 / 后果                                                  |
| ----------------------------------- | ---------------------------- | ------------------------------------------------------------ |
| **Descriptor table**                | **完全拷贝**，子进程独立一份 | 每个进程私有；子进程改 fd 映射不影响父进程                   |
| **Open file table (`struct file`)** | **共用**，refcnt +1          | 父子共享 file pos 和打开标志；一方读写会移动另一方的文件指针 |
| **v-node table (`inode`)**          | **共用**（全局唯一）         | 文件元数据全局共享，与打开无关                               |

### 一个经典陷阱

因为父子共享 `file pos`，如果 fork 之后父子同时对同一个 fd 调用 `write`，输出会**交错**（interleave），而不是各自从头写。如果想要各自独立的偏移量，必须在 fork 之后让子进程重新 `open()` 文件，这样才会创建新的 `struct file`，拥有独立的 `file pos`。

这也是为什么 shell 在 `fork()` 之后、`exec()` 之前要做一系列 `dup2` 重定向——因为描述符表是子进程私有的，可以随意改，而改完后指向的 open file 仍然是共享的（从而实现管道、重定向的衔接）。
