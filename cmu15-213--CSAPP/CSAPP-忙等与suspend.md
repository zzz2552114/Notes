这不是单纯“谁更快”的区别，核心是**正确性 + CPU 效率**的本质差异：

下面详细拆解：

------

### 一、`sigsuspend` 做了什么？为什么能正常退出？

`sigsuspend(&prev)` 是一个**原子操作**，一次性完成两件事：

1. **临时把进程的信号掩码替换为 `prev`**（也就是解除 SIGCHLD 的阻塞，`prev` 是阻塞前的旧掩码）；
2. **立刻让进程进入睡眠（挂起）状态**，直到有信号递达并执行完处理函数，`sigsuspend` 才会返回。

**原子性**是关键：它保证「解除阻塞」和「挂起进程」之间不会被信号打断，不会出现“刚解除阻塞、还没睡着信号就来了，然后永远睡死过去”的竞态问题。

当 SIGCHLD 递达后：

- 内核执行 `sigchld_handler`，在处理函数中给 `pid` 赋非 0 值；
- 处理函数返回后，`sigsuspend` 被唤醒、返回；
- 回到 while 循环判断 `!pid`，此时 pid 非 0，循环正常退出。

------

### 二、如果先解除阻塞再忙等，为什么不如 sigsuspend？

假设我们改成“先解除阻塞，再空转等待”：

```
Sigprocmask(SIG_SETMASK, &prev, NULL); // 先解除阻塞
while (!pid)
    ; // 空转忙等
```

这确实能退出循环，但这是**忙等待（busy waiting）**，问题非常明显：

1. **极度浪费 CPU**：进程会一直霸占 CPU 死循环检查变量，CPU 使用率直接拉满，全做无用功。
2. **反而拖慢整体速度**：如果是单核系统，忙等进程会占住 CPU，导致子进程都抢不到 CPU 运行、退出变慢，整体执行效率反而更低。
3. **响应开销更大**：忙等时 CPU 一直在跑循环，信号到来需要强制打断当前执行、切换到信号处理函数，上下文切换开销更高。

而 `sigsuspend` 是让进程**睡眠让出 CPU**：

- 等待期间进程不占用任何 CPU 时间，内核把 CPU 分给其他需要运行的进程；
- 信号到来时，内核立刻唤醒进程，响应延迟极低；
- 系统整体 CPU 利用率高，程序实际执行效率也更高。

------

### 补充：这段代码的设计目的

这是 CSAPP 里经典的**信号同步**范式，核心解决两个问题：

1. **竞态问题**：用 `sigsuspend` 的原子性，避免“解除阻塞-等待”之间信号提前到达导致的永久阻塞；
2. **效率问题**：用内核挂起等待替代用户态忙等，避免 CPU 空转。
