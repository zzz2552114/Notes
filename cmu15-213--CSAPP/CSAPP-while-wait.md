### 1. while 循环退出的条件

循环条件是 `(pid = wait(NULL)) > 0`，当 `wait()` 返回 `-1` 时，循环就会退出。

`wait()` 返回 `-1` 的**正常场景**只有一种： 当前进程已经**没有任何子进程了**（所有子进程都已经被回收完毕），此时系统会把 `errno` 设置为 `ECHILD`。

这也对应了代码末尾的判断：`if (errno != ECHILD)` —— 正常退出循环时 `errno` 一定是 `ECHILD`，如果不是就说明出现了意料之外的错误。

------

### 2. 为什么不会“一直等待”？

首先明确：`wait(NULL)` 本质是**阻塞系统调用**，它的行为分三种情况：

- 如果当前有**已经退出的僵尸子进程**：立刻回收它，返回子进程 PID，循环继续。
- 如果没有僵尸子进程，但**还有正在运行的子进程**：`wait` 会**阻塞挂起调用进程**，直到有一个子进程退出后才返回。
- 如果**连正在运行的子进程都没有了**：`wait` 会立刻返回 `-1`，不会等待，循环直接退出。

所以：

- 当所有子进程都已经退出时，循环会把它们全部回收，随后 `wait` 发现没有子进程了，立刻返回 `-1`，循环结束，不会一直等待。
- 但如果还有子进程在运行，**这个写法其实是会阻塞等待的**——这是这段示例代码的一个缺陷。

------

### 3. 为什么要用 while 循环？（信号合并问题）

Linux 的标准信号是**不排队**的：如果短时间内有多个子进程同时退出，多个 `SIGCHLD` 信号可能会被合并成一次，只触发一次信号处理函数。

如果只调用一次 `wait`，就只能回收一个子进程，剩下的僵尸进程就会遗留。用 `while` 循环可以一次性把所有已经退出的子进程全部回收干净。

------

### 4. 更标准、安全的写法

这段代码用阻塞的 `wait` 是不严谨的：如果还有子进程没退出，信号处理函数会卡在 `wait` 上，导致主程序被阻塞。

CSAPP 等教材里的标准正确写法是用 `waitpid` 加上 **`WNOHANG` 非阻塞选项**：

```
while ((pid = waitpid(-1, NULL, WNOHANG)) > 0) {
    ccount--;
    // 回收子进程
}
```

`WNOHANG` 的作用是：如果当前没有已经退出的子进程，`waitpid` 立刻返回 `0`，循环退出，**不会阻塞等待还在运行的子进程**，保证信号处理函数能快速返回，不打断主程序逻辑。

------

补充：代码开头保存 `errno`、结尾恢复的写法，是信号处理函数的标准良好实践——避免信号处理函数内部的系统调用修改 `errno`，从而破坏主程序的错误状态。
