# 事务（Transaction）：BEGIN / COMMIT / ROLLBACK

## 1. 是什么？

事务（Transaction）是数据库操作的**最小不可分割工作单元**。它将多条相互关联的 SQL 语句捆绑在一起，这批语句要么**全部执行成功**，要么**全部不执行**，绝对不允许出现"只成功一半"的中间状态。

## 2. 为什么有这个东西？

核心是为了保证数据的**安全性、完整性和一致性（ACID 理论）**。

最经典的例子就是"银行转账"：A 给 B 转账 100 元。

- 操作 1：A 账户余额减 100。
- 操作 2：B 账户余额加 100。

如果操作 1 成功后，突然停电了或者报错了，操作 2 没执行，那么这 100 元就凭空消失了！有了事务，如果操作 2 失败，数据库会自动将操作 1 的状态**回滚（撤销）**，就像一切都没发生过一样。

## 3. 语法是什么？

```sql
-- 开启事务（宣布进入保护伞模式）
BEGIN;  -- 也可以写 START TRANSACTION;

-- 执行各种增删改查
UPDATE accounts SET balance = balance - 100 WHERE name = 'A';
UPDATE accounts SET balance = balance + 100 WHERE name = 'B';

-- 如果确认一切无误，提交事务，永久保存！
COMMIT;

-- 如果中间发现不对劲，或者外部应用捕获了报错，回滚事务，撤销所有修改！
ROLLBACK;
```

## 4. 简单例子：电商下单

假设电商系统有人下单：

```sql
BEGIN;
-- 1. 生成订单记录
INSERT INTO orders (user_id, total) VALUES (99, 500);
-- 2. 扣减商品库存
UPDATE inventory SET stock = stock - 1 WHERE product_id = 10;
-- 此时，如果发现库存不足报错了，我们执行：
ROLLBACK;
-- 如果完全没问题：
COMMIT;
```

## 5. 常见用法是什么？

- **资金/积分变动**：绝对需要事务。A 扣 100、B 加 100，这两步必须同生共死。
- **多表级联写入**：例如注册用户时，不仅在 `users` 表里写入数据，还要在 `user_profiles` 里写入初始资料，还要在 `permissions` 表里写入默认权限。必须用事务包起来——否则 users 写成功了、user_profiles 写失败了，就会出现一个"有账号没资料"的僵尸用户。

```sql
BEGIN;
INSERT INTO users (username, password_hash) VALUES ('newbie', 'xxx');
INSERT INTO user_profiles (user_id, nickname) VALUES (currval('users_id_seq'), '新人');
INSERT INTO permissions (user_id, role) VALUES (currval('users_id_seq'), 'student');
COMMIT;
```

- **危险运维操作的"后悔药"**：你想手动 `UPDATE` 生产环境的一批数据，但不确定 `WHERE` 条件写得对不对。你可以先敲 `BEGIN;`，然后执行 `UPDATE`，接着写一个 `SELECT` 看看改了哪些行。如果发现连全表都改了（没加 WHERE），马上大喊一声 `ROLLBACK;` 救你一命。如果没问题，才 `COMMIT;`。

```sql
BEGIN;
UPDATE students SET major = 'CS' WHERE student_id = 1;
SELECT * FROM students WHERE student_id = 1;  -- 确认改对了
COMMIT;  -- 对了才提交
-- 万一错了：ROLLBACK;
```

## 6. 重要注意事项

- **自动提交（Auto-Commit）坑**：很多客户端工具（如 DataGrip、DBeaver、JDBC 驱动）默认开启了自动提交模式。这意味着你没写 `BEGIN` 时，每执行一条 SQL，工具都会自动在背后偷偷给你加上 `BEGIN` 和 `COMMIT`。因此要测试事务，必须明确手写 `BEGIN;` 或在客户端设置里关闭 Auto-Commit。

- **不能把事务开太久**：事务执行期间，被你 `UPDATE` / `DELETE` 的行往往会被加锁（Lock）。如果你写了 `BEGIN`，改了数据，然后去吃午饭了没 `COMMIT`，其他想要修改这些数据的程序全都会被卡死！**事务要尽可能的短、快**。

- **PostgreSQL 里的神级特性**：在 PostgreSQL 中，你甚至可以在事务里撤销**改表结构（DDL）**！比如 `BEGIN; DROP TABLE students; ROLLBACK;`，表又会回来。而在 MySQL 中，DDL 语句一旦执行会强制立刻提交，无法回滚。

# 进阶一：ACID 原则逐字母深度讲解

ACID 是事务的四大特性，四个字母分别代表：**A**tomicity（原子性）、**C**onsistency（一致性）、**I**solation（隔离性）、**D**urability（持久性）。下面逐个拆开讲透。

## 6.1 原子性（Atomicity）

**定义**：事务里的操作要么全部做完，要么全部不做，不允许停在中间任何一个步骤。

银行转账的例子就是原子性的直接体现：A 扣 100 和 B 加 100 必须是"二合一"的动作，不可能只做一半。

**实现原理（为什么能回滚？）**：

数据库在执行每一条修改之前，会先把"修改前的旧值"记录到一种叫做 **undo log（撤销日志）** 的东西里。一旦你执行 ROLLBACK，数据库就照着 undo log 把数据一条条改回原样。

```text
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE name = 'A';
-- 数据库先往 undo log 写一行："A 原来的余额是 1000"
-- 然后才真正把 A 改成 900
UPDATE accounts SET balance = balance + 100 WHERE name = 'B';
-- 同理写 undo log："B 原来的余额是 500"

ROLLBACK;
-- 数据库照着 undo log 往回改：A 变回 1000，B 变回 500
```

> 注意！！！原子性和"持久性"是一对矛盾：COMMIT 之前的数据都在内存/WAL 里，随时可以回滚；COMMIT 之后就不能再回滚了。undo log 的生命周期就是"事务从 BEGIN 到 COMMIT/ROLLBACK"。

## 6.2 一致性（Consistency）

**定义**：事务执行前后，数据库必须从一个**一致的状态**转到另一个**一致的状态**。所谓"一致"，就是所有约束、规则、业务逻辑都没有被破坏。

什么叫"一致状态"？举例：
- 外键约束：你不能插入一条 orders 记录指向一个不存在的 customer_id。
- CHECK 约束：age 不能是负数。
- 唯一性约束：同一个 email 不能出现两次。
- 业务规则：A 的钱 + B 的钱 = 总资产（转账前后总资产不变）。

```text
转账前：A=1000, B=500, 总资产=1500  ✅ 一致
转账后：A=900,  B=600, 总资产=1500  ✅ 一致
中间态（操作1做完操作2没做）：A=900, B=500, 总资产=1400  ❌ 不一致
```

事务的作用就是把你从"一致状态1"安全地送到"一致状态2"，绝不允许你停在中间那个"不一致状态"。

> 注意！！！一致性是原子性、隔离性、持久性三者共同作用的**最终结果**，而不是一个独立的机制。约束（主键、外键、CHECK、NOT NULL）是数据库层保证一致性的手段，业务规则则需要你用事务来保证。

## 6.3 隔离性（Isolation）

**定义**：多个并发执行的事务之间，互相感知不到对方的中间状态，就好像它们是串行执行的一样。

为什么需要隔离性？因为两个程序同时改同一条数据时，如果不加隔离，就会出现"脏读、不可重复读、幻读"等诡异问题。隔离性有四个级别，级别越高越安全但越慢，下面"进阶二"会详细讲。

## 6.4 持久性（Durability）

**定义**：一旦事务 COMMIT 成功，这个修改就是**永久的**，哪怕数据库立刻崩溃、断电、机器炸了，重启之后数据也不能丢。

**实现原理（怎么保证崩溃不丢？）**：

关键技术叫 **WAL（Write-Ahead Logging，预写式日志）**，PostgreSQL 里也叫 **redo log（重做日志）**。

流程是这样的：

```text
1. 你 UPDATE 了一行，数据库先把"这次修改要做什么"写到 WAL 日志里（顺序写硬盘，很快）
2. WAL 写完并 fsync（强制刷到物理磁盘，而不是只停在操作系统缓存）
3. 然后才真正去改内存里的数据页（shared_buffers）
4. COMMIT 返回成功
```

关键点：**WAL 是先写的**。即使改内存那一步还没来得及刷到数据文件，机器就崩了，重启后数据库会读 WAL 日志，把没做完的修改"重做"一遍，数据就回来了。

> 注意！！！持久性的代价就是 fsync。每次 COMMIT 都要等一次磁盘刷盘，这是事务"慢"的根本原因之一。这也是为什么"不能把事务开太久"——事务里做的修改越多，COMMIT 时要刷的 WAL 越多。

# 进阶二：事务隔离级别（Isolation Levels）

并发访问同一份数据时，会出现三种"异常现象"：脏读、不可重复读、幻读。四个隔离级别就是用来逐级解决这三种异常的。

## 7.1 三种并发异常详解

### 7.1.1 脏读（Dirty Read）

**定义**：A 事务读到了 B 事务**还没提交**的修改，然后 B 事务回滚了，A 读到的就是一笔"从来没存在过"的脏数据。

详细示例：

```text
时刻   事务A（张三）                    事务B（李四）
t1                                    BEGIN;
t2                                    UPDATE account SET balance = 1000 WHERE id = 1;
t3   SELECT balance FROM account WHERE id = 1;  → 读到 1000
t4                                    ROLLBACK;  -- 李四反悔了，改回去了
t5   张三拿这个 1000 去做业务判断...    -- 完了！这个 1000 是假的
```

李四把余额改成 1000 但还没提交，张三就读到了 1000。结果李四回滚，余额实际是 500，但张三已经基于"假的 1000"做了决策。

### 7.1.2 不可重复读（Non-repeatable Read）

**定义**：A 事务内，**同一个查询执行了两次**，中间 B 事务提交了一次 UPDATE，导致 A 两次读到的同一行数据不一样。

详细示例：

```text
时刻   事务A（张三）                    事务B（李四）
t1   BEGIN;
t2   SELECT balance FROM account WHERE id = 1;  → 读到 500
t3                                    BEGIN;
t4                                    UPDATE account SET balance = 1000 WHERE id = 1;
t5                                    COMMIT;  -- 李四正式提交了
t6   SELECT balance FROM account WHERE id = 1;  → 读到 1000 ！！
```

张三在同一个事务里查了两次同一条记录，结果不一样。问题出在李四在中间提交了一次修改。

> 注意！！！不可重复读和脏读的区别：脏读读的是"别人没提交的"，不可重复读读的是"别人已提交的 UPDATE"。不可重复读针对的是**同一行数据被 UPDATE 了**。

### 7.1.3 幻读（Phantom Read）

**定义**：A 事务内，**同一个范围查询执行了两次**，中间 B 事务提交了 INSERT/DELETE 符合该条件的行，导致 A 两次查到的**行数不一样**，就像"幻影"一样多出来一批行。

详细示例：

```text
时刻   事务A（张三）                    事务B（李四）
t1   BEGIN;
t2   SELECT COUNT(*) FROM account WHERE balance > 100;  → 10 行
t3                                    BEGIN;
t4                                    INSERT INTO account (balance) VALUES (200);
t5                                    COMMIT;
t6   SELECT COUNT(*) FROM account WHERE balance > 100;  → 11 行 ！！
```

张三两次 COUNT，条件一模一样，结果从 10 变成 11，凭空多出来一行"幻影"。

> 注意！！！幻读和不可重复读的区别：不可重复读是**同一行**被 UPDATE 了（值变了），幻读是**多了或少了几行**（行数变了，通常是 INSERT/DELETE 造成的）。

### 7.1.4 三者对比表

| 异常 | 本质 | 谁干的 | 针对什么 |
|---|---|---|---|
| 脏读 | 读到别人未提交的修改 | 别的事务 ROLLBACK 了 | 读了"假数据" |
| 不可重复读 | 同一行两次读值不同 | 别的事务 COMMIT 了 UPDATE | 同一行被改了 |
| 幻读 | 同一范围两次行数不同 | 别的事务 COMMIT 了 INSERT/DELETE | 多了/少了几行 |

## 7.2 四个隔离级别

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 性能 |
|---|---|---|---|---|
| READ UNCOMMITTED（读未提交） | 可能发生 | 可能发生 | 可能发生 | 最高 |
| READ COMMITTED（读已提交） | 解决 | 可能发生 | 可能发生 | 高 |
| REPEATABLE READ（可重复读） | 解决 | 解决 | 理论上可能发生 | 中 |
| SERIALIZABLE（可串行化） | 解决 | 解决 | 解决 | 最低 |

各数据库的默认级别：

| 数据库 | 默认隔离级别 |
|---|---|
| PostgreSQL | READ COMMITTED |
| MySQL InnoDB | REPEATABLE READ |
| Oracle | READ COMMITTED |
| SQL Server | READ COMMITTED |

### 7.2.1 READ UNCOMMITTED（读未提交）

最低级别。一个事务可以读到其他事务**还没提交**的数据。脏读就发生在这里。几乎没有数据库会把它作为默认级别，实际开发中也几乎不用。

```sql
-- 设置隔离级别（PostgreSQL 语法）
BEGIN TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
```

### 7.2.2 READ COMMITTED（读已提交）

PostgreSQL 的默认级别。一个事务只能读到其他事务**已经提交**的数据。

- 解决了脏读：你读的时候，别人没提交的修改你看不见。
- 但还存在不可重复读：你在事务内第二次读的时候，别人已经提交的 UPDATE 你就能看到了。

```sql
BEGIN TRANSACTION ISOLATION LEVEL READ COMMITTED;
-- 或者用简写
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

> 注意！！！READ COMMITTED 是 PostgreSQL 的默认级别，也是大多数互联网业务的首选——它在并发性能和数据一致性之间取得了最好的平衡。

### 7.2.3 REPEATABLE READ（可重复读）

MySQL InnoDB 的默认级别。在这个级别下，事务内多次读同一数据，结果一致——因为整个事务看到的是**事务开始那一刻的数据快照**。

- 解决了脏读和不可重复读。
- 理论上还存在幻读（但 MySQL InnoDB 通过 MVCC + Next-Key Lock 在很大程度上避免了幻读；PostgreSQL 的 REPEATABLE READ 也通过快照隔离避免了幻读）。

```sql
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

### 7.2.4 SERIALIZABLE（可串行化）

最高级别。强制事务串行执行，完全避免所有并发异常。但性能最低，因为并发度被压到了 1。

```sql
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

> 注意！！！PostgreSQL 的 SERIALIZABLE 并不是真的把事务排成一队一个一个跑，而是用 SSI（可序列化快照隔离）技术在 MVCC 之上检测危险的读写依赖，发现可能出问题就回滚其中一个事务。后面"进阶六"会详细讲。

## 7.3 设置事务隔离级别

```sql
-- 方式一：在 BEGIN 时指定（推荐，只影响当前事务）
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- 方式二：在事务内部设置
START TRANSACTION;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- 方式三：设置整个会话的默认级别
SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

# 进阶三：MVCC 多版本并发控制

PostgreSQL（以及 MySQL InnoDB）之所以能做到"读写不互相阻塞"，全靠 MVCC（Multi-Version Concurrency Control，多版本并发控制）。

## 8.1 MVCC 原理

传统的锁机制：一个事务在改一行，其他事务想读这行就得排队等。

MVCC 的做法：**不覆盖旧数据，而是保留多个版本**。当事务 A 修改一行时，数据库不直接删掉旧版本，而是把旧版本保留在那里，给新版本打上新事务的标记。这样：

- 读事务看到的是"它开始那一刻"的快照（旧版本）。
- 写事务生成新版本，不影响正在读的旧版本。
- 读写互不阻塞！

## 8.2 快照（Snapshot）

事务开始时（在 REPEATABLE READ 及以上级别），数据库会拍一张"快照"——记录此刻哪个事务是活跃的、哪个已经提交了。之后这个事务再怎么查，看到的都是快照那一刻的数据状态，不管别人中间提交了多少修改。

## 8.3 事务 ID 与 xmin / xmax

PostgreSQL 的每一行数据（在 heap 表里）都隐藏了两个系统列：

- **xmin**：插入这一行的事务 ID。
- **xmax**：删除/过期这一行的事务 ID（没被删过时为 0）。

```sql
-- 你可以直接查看这两个隐藏列
SELECT xmin, xmax, student_id, student_name FROM students;
```

可见性判断规则（简化版）：

```text
对当前事务 T 来说，一行数据可见当且仅当：
1. xmin < T 且插入 xmin 的事务已经提交  （这行是"过去"插的）
2. 并且 (xmax 为 0  或者  xmax >= T  或者  删除 xmax 的事务还没提交)
   （这行没被"未来"的事务删掉）
```

举例：
- 事务 100 插入了一行，xmin=100。
- 事务 200 开始查数据（快照里 100 已提交）。这行 xmin=100 < 200 且已提交，xmax=0，可见。
- 事务 300 DELETE 了这行，把 xmax 改成 300。
- 事务 200 再查，xmax=300 > 200，这行对 200 仍然可见（因为 200 开始时这行还没被删）。
- 事务 400 开始查，xmax=300 < 400 且 300 已提交，这行对 400 不可见。

## 8.4 MVCC 的优势和代价

**优势**：
- 读写不阻塞：读的人不等写的人，写的人不等读的人。并发性能极高。
- 读操作不加锁：普通 SELECT 不会锁任何行。

**代价**：
- 行版本膨胀（bloat）：UPDATE 不是原地改，而是生成新版本、旧版本标记为死亡。表里会堆积大量"死元组"（dead tuples）。
- 需要 VACUUM 清理：死元组不能永远占着硬盘，PostgreSQL 用 VACUUM 进程回收它们。
- 长事务会阻止 VACUUM：如果一个事务开了很久，它的快照还"看着"那些早就该被清理的旧版本，VACUUM 就不敢回收——这就是长事务导致表膨胀的根本原因（见"进阶十"）。

# 进阶四：锁的类型

## 9.1 行锁（Row Lock）

普通的 `UPDATE`/`DELETE` 会自动给命中的行加行锁。你也可以在 SELECT 时显式加行锁：

| 语法 | 锁类型 | 含义 |
|---|---|---|
| `SELECT ... FOR UPDATE` | 排他行锁 | 锁定这些行，阻止其他事务再改/再加锁 |
| `SELECT ... FOR NO KEY UPDATE` | 弱排他锁 | 比 FOR UPDATE 弱，不阻塞 FOR KEY SHARE |
| `SELECT ... FOR SHARE` | 共享行锁 | 允许其他事务读，但阻止其他事务改 |
| `SELECT ... FOR KEY SHARE` | 弱共享锁 | 最弱的锁，只阻止 FOR UPDATE |

典型场景：先查后改的竞态条件。

```sql
-- 两个事务同时要扣库存，如果不加锁：
-- 事务A：SELECT stock FROM inventory WHERE product_id = 10;  → 读到 5
-- 事务B：SELECT stock FROM inventory WHERE product_id = 10;  → 也读到 5
-- 两边都算完要扣到 4，结果 COMMIT 后库存只少了 1，错！

-- 正确做法：SELECT ... FOR UPDATE 把行锁住
BEGIN;
SELECT stock FROM inventory WHERE product_id = 10 FOR UPDATE;  -- 其他事务在这里卡住
-- 假设读到 5，扣成 4
UPDATE inventory SET stock = 4 WHERE product_id = 10;
COMMIT;
```

`FOR UPDATE` 的两个变体：

```sql
-- NOWAIT：拿不到锁就立刻报错，不等（适合不想被卡住的场景）
SELECT * FROM accounts WHERE id = 1 FOR UPDATE NOWAIT;

-- SKIP LOCKED：跳过已经被锁住的行（任务队列 worker 抢任务的经典用法）
UPDATE tasks SET status = 'running'
WHERE id = (SELECT id FROM tasks WHERE status = 'pending' ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED)
RETURNING id;
```

> 注意！！！`FOR UPDATE` 必须在事务里用，否则 SELECT 完锁就释放了，等于没锁。

## 9.2 表锁（Table Lock）

PostgreSQL 有八档表锁，从弱到强：

| 锁模式 | 谁会拿 | 阻塞谁 |
|---|---|---|
| ACCESS SHARE | 普通 SELECT | 只阻塞 ACCESS EXCLUSIVE |
| ROW SHARE | SELECT ... FOR UPDATE/SHARE | 阻塞 ACCESS EXCLUSIVE |
| ROW EXCLUSIVE | INSERT/UPDATE/DELETE | 阻塞 SHARE 及以上 |
| SHARE UPDATE EXCLUSIVE | VACUUM(without FULL)、ANALYZE | 阻塞同类和 SHARE 以上 |
| SHARE | CREATE INDEX（普通） | 阻塞 ROW EXCLUSIVE 及以上 |
| SHARE ROW EXCLUSIVE | 很少用 | 阻塞 ROW EXCLUSIVE、SHARE 及以上 |
| EXCLUSIVE | 很少用 | 阻塞除 ACCESS SHARE 外的所有 |
| ACCESS EXCLUSIVE | DROP TABLE、ALTER TABLE、VACUUM FULL、LOCK TABLE | 阻塞一切 |

> 注意！！！`ALTER TABLE`、`DROP TABLE` 会拿 ACCESS EXCLUSIVE 锁，**阻塞所有读写**。在大表上做 DDL 一定要小心，最好用 `CONCURRENTLY` 或在低峰期做。

手动加表锁：

```sql
BEGIN;
LOCK TABLE students IN SHARE ROW EXCLUSIVE MODE;
-- 做一些需要保护整表的操作
COMMIT;
```

## 9.3 咨询锁（Advisory Lock）

咨询锁是应用层自己定义的锁，数据库不强制，全靠应用自觉配合。适合"跨会话协调某个业务资源"。

```sql
-- 会话 A：拿到一个以 12345 为标识的咨询锁
SELECT pg_advisory_lock(12345);
-- 做一些关键操作...
SELECT pg_advisory_unlock(12345);

-- 会话 B：如果 A 没释放，这一行会阻塞等待
SELECT pg_advisory_lock(12345);
```

还有带超时的版本：`pg_try_advisory_lock(12345)`，拿不到立刻返回 false 而不是卡住。

# 进阶五：死锁检测与处理

## 10.1 死锁怎么产生的

两个事务，各自持有一把锁，又互相等对方手里的锁，就僵住了：

```text
时刻   事务A                          事务B
t1   BEGIN;
t2   UPDATE accounts SET balance=900 WHERE id=1;  -- 锁住行1
t3                                 BEGIN;
t4                                 UPDATE accounts SET balance=600 WHERE id=2;  -- 锁住行2
t5   UPDATE accounts SET balance=... WHERE id=2;  -- 想要行2，等B释放
t6                                 UPDATE accounts SET balance=... WHERE id=1;  -- 想要行1，等A释放
-- 双方都在等对方，永久卡死！这就是死锁
```

## 10.2 PostgreSQL 的死锁检测

PostgreSQL 有一个后台检测器，默认每 `deadlock_timeout`（默认 1 秒）检查一次是否有死锁循环。一旦发现，会**主动选择其中一个事务作为牺牲品**，把它 ROLLBACK，释放它持有的锁，让另一个事务能继续走。

报错长这样：

```text
ERROR: deadlock detected
DETAIL: Process 12345 waits for ShareLock on transaction 6789; blocked by process 6789.
Process 6789 waits for ShareLock on transaction 12345; blocked by process 12345.
```

## 10.3 死锁预防策略

1. **统一加锁顺序**：所有事务都按相同的顺序给行加锁（比如永远先锁 id 小的，再锁 id 大的），就不会出现循环等待。
2. **事务尽量短**：持锁时间越短，死锁窗口越小。
3. **降低隔离级别**：必要时用 READ COMMITTED 而非 SERIALIZABLE。
4. **给 SQL 加合适的索引**：如果 UPDATE 走全表扫描，会锁住更多行，死锁概率大增。

详细示例——统一加锁顺序：

```sql
-- 错误：两个事务加锁顺序相反
-- 事务A：先锁 id=1 再锁 id=2
-- 事务B：先锁 id=2 再锁 id=1  → 可能死锁

-- 正确：永远按 id 升序加锁
-- 事务A：SELECT ... WHERE id IN (1,2) ORDER BY id FOR UPDATE;
-- 事务B：SELECT ... WHERE id IN (1,2) ORDER BY id FOR UPDATE;
-- 两边都先锁 id=1，谁先拿到谁先做，另一个排队，不会死锁
```

# 进阶六：SERIALIZABLE 与 SSI（可序列化快照隔离）

PostgreSQL 的 SERIALIZABLE 级别并不是真的把事务排成一个队列串行跑（那样性能太差）。它用的是 **SSI（Serializable Snapshot Isolation，可序列化快照隔离）**。

## 11.1 SSI 原理

每个事务还是基于自己的快照跑（像 REPEATABLE READ 一样），但数据库会在背后监控事务之间的**读写依赖**（rw-dependency）：

- 事务 A 读了某些行，事务 B 又改了这些行并提交了 → 存在一条 "A reads from B 的旧版本，B 写了新值" 的危险依赖。
- 如果检测到这种依赖形成了一个"环"（可能导致非串行化执行结果），数据库会**主动回滚其中一个事务**。

## 11.2 与真串行执行的区别

| | 真串行执行 | SSI |
|---|---|---|
| 并发度 | 1（一次一个事务） | 高（大家并行跑，只在危险时回滚） |
| 异常率 | 0 | 偶尔需要重试 |
| 性能 | 极差 | 接近 READ COMMITTED |

被 SSI 回滚的事务会收到这样的错误：

```text
ERROR: could not serialize access due to read/write dependencies among transactions
```

应用程序遇到这个错误应该**自动重试整个事务**。

# 进阶七：自动提交模式详解

## 12.1 什么是自动提交

自动提交（Auto-Commit）模式下，每条 SQL 语句都被当作一个独立的事务：执行完立刻 COMMIT。你不写 BEGIN，数据库就帮你每条 SQL 都 BEGIN+COMMIT。

## 12.2 各客户端默认行为

| 客户端/驱动 | 默认是否自动提交 |
|---|---|
| psql（命令行） | 是 |
| DataGrip / DBeaver | 是（但有按钮可以切到手动手动提交） |
| JDBC | 是 |
| Python psycopg2 | **否**！psycopg2 默认关闭自动提交，必须手动 conn.commit() |
| Go lib/pq | 是 |

> 注意！！！Python 用 psycopg2 时，你执行完 INSERT 不写 `conn.commit()`，数据根本不会真正写进去——这是无数新手踩过的坑。

## 12.3 如何关闭自动提交

```sql
-- PostgreSQL 会话级关闭
SET AUTOCOMMIT = OFF;
-- 之后每条 SQL 不会自动提交，直到你显式 BEGIN/COMMIT
```

## 12.4 自动提交的性能影响

自动提交模式下，每条 INSERT 都要一次 fsync，批量插入会慢到死。正确做法是手动 BEGIN，把几百上千条 INSERT 包在一个事务里，最后一次 COMMIT——这就是"批量导入为什么要包事务"的原理。

```sql
-- 慢：每条 INSERT 一次 fsync
INSERT INTO logs VALUES (...);
INSERT INTO logs VALUES (...);
INSERT INTO logs VALUES (...);

-- 快：一次 fsync
BEGIN;
INSERT INTO logs VALUES (...);
INSERT INTO logs VALUES (...);
INSERT INTO logs VALUES (...);
COMMIT;
```

# 进阶八：DDL 语句的事务行为

## 13.1 PostgreSQL：DDL 可以回滚

PostgreSQL 把 DDL（CREATE/ALTER/DROP TABLE）也当做普通 SQL 一样纳入事务管理：

```sql
BEGIN;
DROP TABLE students;
-- 此时 students 真的没了，但只在当前会话里
-- 如果你后悔了：
ROLLBACK;
-- students 表又回来了！
```

```sql
BEGIN;
ALTER TABLE students ADD COLUMN temp_col INTEGER;
-- 加了一列，检查一下...
-- 不对，不该加这列
ROLLBACK;
-- 列又没了
```

## 13.2 MySQL：DDL 隐式提交

在 MySQL 中，你执行任何 DDL 语句，它都会**先自动 COMMIT 当前事务**，然后执行 DDL，再自动 COMMIT。所以 DDL 一旦执行就无法回滚：

```sql
-- MySQL 里：
BEGIN;
UPDATE students SET major='Math' WHERE student_id=1;
CREATE TABLE temp (id INT);  -- 这条 DDL 隐式 COMMIT 了上面的 UPDATE！
-- 此时你想 ROLLBACK，UPDATE 已经提交了，撤不回来了！
ROLLBACK;  -- 只回滚了 CREATE TABLE 之后的东西，UPDATE 已经永久生效
```

## 13.3 各数据库差异对比

| 数据库 | DDL 能否回滚 |
|---|---|
| PostgreSQL | 能 |
| MySQL | 不能（隐式提交） |
| Oracle | 部分能（DDL 执行后自动 COMMIT，但 Oracle 内部其实有 SAVEPOINT） |
| SQL Server | 能（DDL 在事务内） |

## 13.4 PostgreSQL DDL 事务的实际应用：原子性 schema 迁移

因为 PG 的 DDL 能回滚，你可以写一个"要么全成功、要么全不做"的数据库迁移脚本：

```sql
BEGIN;
ALTER TABLE students ADD COLUMN email_verified BOOLEAN NOT NULL DEFAULT FALSE;
ALTER TABLE students ALTER COLUMN email TYPE VARCHAR(200);
CREATE INDEX idx_students_email ON students(email);
-- 全部成功才 COMMIT，任何一步报错都整体回滚，数据库不会停在半改状态
COMMIT;
```

# 进阶九：SAVEPOINT 保存点（部分回滚）

## 14.1 语法

```sql
SAVEPOINT 保存点名字;       -- 在事务内打一个标记
ROLLBACK TO SAVEPOINT 名字;  -- 回滚到这个标记，但事务不结束
RELEASE SAVEPOINT 名字;      -- 删掉这个标记（事务继续）
```

## 14.2 原理和用途

有时候一个事务很长，你希望"其中某几步错了就撤销那几步，但不要把整个事务都回滚"。SAVEPOINT 就是事务内的"后悔药中的后悔药"。

## 14.3 详细示例

```sql
BEGIN;

INSERT INTO users (username) VALUES ('alice');  -- 第一步：注册
SAVEPOINT after_user;

INSERT INTO user_profiles (user_id, nickname) VALUES (1, 'Alice');  -- 第二步：建资料
-- 假设这步因为某种原因失败了
-- 你不想把整个事务回滚（因为第一步注册是好的），只想撤销第二步：
ROLLBACK TO SAVEPOINT after_user;
-- 现在回到了刚插完 users 的状态，user_profiles 那条没插进去

-- 换个方式再试一次
INSERT INTO user_profiles (user_id, nickname) VALUES (1, 'A');

COMMIT;  -- users 和 user_profiles 都最终提交了
```

## 14.4 保存点的性能影响

SAVEPOINT 本身开销很小，但 `ROLLBACK TO SAVEPOINT` 会撤销从保存点到现在的所有修改，该做的 undo 还是得做。不要在一个事务里建几百个保存点，那会让 undo log 变得很复杂。

# 进阶十：长事务的危害

## 15.1 长事务到底有多毒

一个事务开了很久不 COMMIT/ROLLBACK，会引发一连串问题：

1. **锁持有时间长**：事务 UPDATE 过的行一直锁着，其他事务想改就卡死。
2. **MVCC 死元组无法回收**：VACUUM 不敢清理"长事务快照还看着"的旧版本，导致表越来越大（膨胀）。
3. **复制延迟**：主库的 WAL 迟迟不归档，从库追不上。
4. ** replication slot 堆积**：逻辑复制槽会一直保留 WAL。

## 15.2 如何监控长事务

```sql
-- 查看所有正在运行的事务，按持续时间排序
SELECT
    pid,
    now() - xact_start AS xact_duration,   -- 事务已经开了多久
    now() - query_start AS query_duration, -- 当前 SQL 跑了多久
    state,
    query
FROM pg_stat_activity
WHERE state != 'idle'
ORDER BY xact_duration DESC NULLS LAST;
```

`idle in transaction` 状态是最危险的——事务开着但没在干活，白白占着锁和快照。

## 15.3 如何处理长事务

```sql
-- 实在没办法就强行终止这个事务
SELECT pg_terminate_backend(pid);  -- 粗暴断开连接
-- 或者温和一点：
SELECT pg_cancel_backend(pid);     -- 只取消当前查询，不断连接
```

> 注意！！！开发时最常见的长事务来源：在 REPL/Notebook 里 BEGIN 了之后去干别的（喝水、开会、写代码），忘了 COMMIT。养成"事务尽量短"的肌肉记忆。

# 进阶十一：其他事务控制语句

## 16.1 SET TRANSACTION

```sql
-- 设置下一个事务的隔离级别、读写模式
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ READ WRITE;
-- READ ONLY 模式下事务不能写，有时能加速只读分析查询
```

## 16.2 SET CONSTRAINTS

外键约束默认在每条语句结束时检查。你可以把它推迟到 COMMIT 时再检查：

```sql
BEGIN;
-- 假设要先删子表再删父表，但外键约束不允许你删父表（还有子表引用它）
-- 把约束推迟到提交时检查：
SET CONSTRAINTS ALL DEFERRED;

DELETE FROM enrollments WHERE student_id = 1;  -- 先删子表
DELETE FROM students WHERE student_id = 1;      -- 再删父表（中间状态不检查）
COMMIT;  -- 提交时才检查，此时两边都删干净了，没问题
```

注意：只有 `DEFERRABLE` 的约束才能这么用，建表时要声明：

```sql
CREATE TABLE enrollments (
    student_id INT REFERENCES students(student_id) DEFERRABLE
);
```

## 16.3 两阶段提交（2PC）

分布式事务的基础。当一个事务要跨多个数据库节点时，用 PREPARE + COMMIT PREPARED：

```sql
-- 第一阶段：准备（不真正提交）
PREPARE TRANSACTION 'txn_1';

-- 第二阶段：所有节点都准备好后，统一提交
COMMIT PREPARED 'txn_1';
-- 或者
ROLLBACK PREPARED 'txn_1';
```
