# 数据增删改（INSERT / UPDATE / DELETE / INSERT ... SELECT）

---

# 第一部分：INSERT——往表里放数据

表建好以后是空的，往后所有查询都会没有结果，所以先把数据放进去。SQL 往表里放数据的语句是：

```sql
INSERT INTO students
    (student_name, email, age, major)
VALUES
    ('Alice', 'alice@example.com', 20, 'CS');
```

## 1. 语法骨架

```text
INSERT INTO 表
    (列1, 列2, 列3)
VALUES
    (值1, 值2, 值3);
```

拆开看每一块：

```text
INSERT      → 动词：插入
INTO        → 方向：插到哪里去
students    → 目标表
(...)       → 这次要给的列
VALUES      → 后面是"一行行具体的值"
```

## 2. INTO 与 FROM 的方向感记忆法

`INTO` 不是凭空来的。SQL 里**凡是"把东西放进某个目标"的动作，都会用 `INTO` 标记目的地**。所以除了 `INSERT INTO`，你后面还会见到 `MERGE INTO`（合并进目标表）、`SELECT ... INTO`（把结果存进变量或新表）。反过来，`FROM` 永远表示"从哪里取"。一句话：

```text
INTO → 目标（去向）
FROM → 来源（来处）
```

记住这个方向感，就不用背"INSERT 后面为什么非要加 INTO"。

## 3. 三件最值得养成的习惯

1. **尽量显式写列名。** 不要养成：

   ```sql
   INSERT INTO students
   VALUES (...);
   ```

   这种完全依赖列顺序的写法。一旦以后表里加了列、改了顺序，这种语句就会悄悄插错位置。

2. **给了值的列，才写进去。** 没写的列如果定义了 `DEFAULT`，数据库会用默认值；如果允许 NULL，就填 NULL。`student_id` 有 `GENERATED ... AS IDENTITY`，`created_at` 有 `DEFAULT CURRENT_TIMESTAMP`，插入时都不需要手动填。

3. **默认值和自动生成，是数据库在替你补全"理所当然"的部分。** 能由数据库保证的规则，尽量别留给写代码的人去记。

## 4. 一次插多行

```sql
INSERT INTO students
    (student_name, email, age, major)
VALUES
    ('Alice', 'alice@example.com', 20, 'CS'),
    ('Bob', 'bob@example.com', 19, 'Math'),
    ('Carol', 'carol@example.com', 21, 'Physics');
```

`VALUES` 后面其实是一张"临时的小表"，每一对括号就是一行。一次性插入多行，本质上只是把这张小表写长一点，而不是重复执行很多次 `INSERT`。

# 第二部分：UPDATE——改数据

```sql
UPDATE students
SET age = age + 1
WHERE student_id = 1;
```

理解：

```text
UPDATE → 改哪张表
SET    → 改成什么
WHERE  → 改哪些行
```

## 最大的危险

```sql
UPDATE students
SET age = age + 1;
```

因为没有 WHERE：

> 所有人都改。

所以初学阶段：

```text
UPDATE / DELETE 写完后，第一反应检查 WHERE。
```

**注意！！！** 忘写 WHERE 的 UPDATE 是全表更新，忘写 WHERE 的 DELETE 是全表删除，这是数据库操作里代价最高的两个低级错误。务必形成肌肉记忆：写完 UPDATE/DELETE，先看 WHERE 在不在。

# 第三部分：DELETE——删数据

```sql
DELETE FROM students
WHERE student_id = 1;
```

## 1. 为什么 DELETE 要写 FROM，而 UPDATE 不用？

这里写作 `DELETE FROM`，而 `UPDATE` 是直接 `UPDATE students SET ...`。看起来不对称，但其实是故意的：

```text
UPDATE 表 SET ...     → 改的是这张表自己
DELETE FROM 表        → 从这张表里把行拿走
INSERT INTO 表        → 往这张表里放行
```

`FROM` 表示"来源"，`INTO` 表示"去向"。`DELETE` 是"从表里取走"，所以配 `FROM`；`UPDATE` 改的是表本身，不需要方向介词。把这三个介词放在一起看，比单独背三条语法更省力。

## 2. 忘写 WHERE 的后果

如果没有 WHERE：

```sql
DELETE FROM students;
```

就是删除整张表里的所有行。

这和：

```sql
DROP TABLE students;
```

不是一回事。

## 3. DELETE vs TRUNCATE vs DROP TABLE

这是非常容易混淆的一组：

```text
DELETE
    删除行，表还在

TRUNCATE
    快速清空表，表还在

DROP TABLE
    表本身没了
```

记忆：

```text
DELETE → 扔数据
TRUNCATE → 清空
DROP → 拆掉整个表
```

| 操作 | 表结构还在吗 | 数据还在吗 | 能加 WHERE 吗 | 速度 |
|---|---|---|---|---|
| `DELETE FROM t` | 在 | 删行 | 能 | 慢（逐行记日志） |
| `TRUNCATE TABLE t` | 在 | 全删 | 不能 | 极快 |
| `DROP TABLE t` | 没了 | 没了 | 不能 | 极快 |

# 第四部分：INSERT ... SELECT——把查询结果写回表

之前我们通过 `INSERT INTO ... VALUES (...)` 手动一条条插入数据。但如果数据已经存在于其他表里（或者可以通过某个复杂的 SQL 算出来），我们可以直接将 `SELECT` 的结果集作为 `INSERT` 的数据源，一键批量插入。

## 核心语法

```sql
INSERT INTO target_table (col1, col2, col3)
SELECT expr1, expr2, expr3
FROM source_table
WHERE ...;
```

## 1. 各种用法与常用情境

- **数据备份与归档（Archive）**：年底到了，我们需要把 2022 年之前的订单全部挪到一张叫 `orders_archive` 的表里。

  ```sql
  INSERT INTO orders_archive (order_id, user_id, amount, created_at)
  SELECT order_id, user_id, amount, created_at
  FROM orders
  WHERE created_at < '2023-01-01';
  ```

- **数据清洗与转换**：原本的表设计不好，或者需要把多张表的数据聚合后存入一张新表。你可以用复杂的 `JOIN`、`GROUP BY` 写一个查询，直接 `INSERT` 进新表。

- **批量复制数据进行测试**：在开发时，为了不污染线上数据，可以根据线上数据衍生出一批测试数据。我们可以在 `SELECT` 中利用字符串拼接、加减法来生成测试数据。例如把所有 CS 专业学生复制成"Copy"测试学生：

  ```sql
  INSERT INTO students (student_name, email, age, major)
  SELECT student_name || ' Copy',
         'copy_' || email,
         age,
         major
  FROM students
  WHERE major = 'CS';
  ```

## 2. 注意事项与重点

- **列的数量与顺序严格对应**：`INSERT INTO` 后面括号里的列名顺序，必须与 `SELECT` 选出的列**顺序严格一致，数量相等**。
- **列名不重要，数据类型最重要**：`SELECT` 出来的列名是什么根本无所谓（因为数据是按顺序填坑的），但**数据类型必须兼容**。
- **自增主键（IDENTITY/SERIAL）**：通常不要在 `INSERT INTO` 的列里写自增主键，让数据库自动生成即可。但如果必须写（例如数据迁移），要确保目标表的主键不会发生冲突。

# 第五部分：进阶——多表关联的 UPDATE 与 DELETE

## 1. UPDATE ... FROM（多表关联更新）

普通 UPDATE 只能改一张表。但如果你要"根据另一张表的数据来更新这张表"，PostgreSQL 提供 `UPDATE ... FROM`：

```sql
-- 把每个学生的总选课数回填到 students 表的一个统计列
UPDATE students AS s
SET course_count = e.cnt
FROM (
    SELECT student_id, COUNT(*) AS cnt
    FROM enrollments
    GROUP BY student_id
) AS e
WHERE s.student_id = e.student_id;
```

意思：先在 FROM 里算出每个学生的选课数，再和 students 按 student_id 对上，把值填进去。

**注意！！！** `SET` 后面的列名不要加表别名前缀（写 `SET course_count =` 而不是 `SET s.course_count =`），这是 PostgreSQL UPDATE 的语法坑。

## 2. DELETE ... USING（多表关联删除）

类似地，想"根据另一张表删除本表的行"，用 `DELETE ... USING`：

```sql
-- 删除所有已毕业学生的选课记录
DELETE FROM enrollments AS e
USING students AS s
WHERE e.student_id = s.student_id
  AND s.status = 'graduated';
```

`USING` 引入要关联的表，`WHERE` 描述连接条件和过滤条件。

# 第六部分：进阶——UPSERT（ON CONFLICT）与 RETURNING

## 1. ON CONFLICT（存在则更新，不存在则插入）

这是 PostgreSQL 非常强大的特性，俗称 UPSERT。经典痛点：往一张有主键/唯一约束的表里插数据，如果主键已存在，普通 INSERT 会报错。`ON CONFLICT` 让你优雅处理：

```sql
-- 主键冲突时什么都不做
INSERT INTO students (student_id, age)
VALUES (1, 18)
ON CONFLICT (student_id) DO NOTHING;

-- 主键冲突时改成更新年龄
INSERT INTO students (student_id, age)
VALUES (1, 18)
ON CONFLICT (student_id) DO UPDATE
SET age = EXCLUDED.age;
```

- `ON CONFLICT (student_id)`：指定"哪个唯一约束冲突时触发"（冲突目标 conflict_target）。
- `DO NOTHING`：冲突就跳过。
- `DO UPDATE SET ...`：冲突就更新。
- `EXCLUDED`：一个特殊的伪表，代表"本来要插入、但被冲突挡下来的那行数据"。`EXCLUDED.age` 就是你想插入的那个新年龄。

**注意！！！** 这条语句"不存在则插入，存在则更新"，一条搞定，而且**绝对并发安全**。在应用层先 SELECT 判断再 INSERT，在高并发下会有两个请求同时判断"不存在"然后双双插入而报错；`ON CONFLICT` 从数据库层面原子地解决这个问题。

## 2. RETURNING（返回刚写入/修改/删除的数据）

PostgreSQL 特有。普通 INSERT/UPDATE/DELETE 只返回"影响了几行"，但应用程序常常需要知道"刚插入的那条记录的自增 id 是多少"。`RETURNING` 解决这个：

```sql
-- 插入后返回自动生成的 student_id
INSERT INTO students (student_name, email)
VALUES ('Alice', 'alice@example.com')
RETURNING student_id;

-- 更新后返回被改的行
UPDATE students
SET age = age + 1
WHERE student_id = 1
RETURNING student_name, age;

-- 删除后返回被删的行
DELETE FROM students
WHERE student_id = 1
RETURNING *;
```

`RETURNING *` 返回整行，`RETURNING col1, col2` 返回指定列。这在应用程序里非常实用——插入一条订单后立刻拿到它的 id，不用再查一次。

# 第七部分：进阶——TRUNCATE 与 DELETE 的深度区别

表面上 `DELETE FROM t` 和 `TRUNCATE TABLE t` 都是清空表，但底层差别巨大：

| 对比维度 | DELETE | TRUNCATE |
|---|---|---|
| 删除方式 | 逐行删除 | 直接释放整表数据页 |
| 事务日志 | 每行记一条日志 | 只记很少量日志 |
| 速度 | 慢（大表明显） | 极快（几乎瞬间） |
| 锁级别 | 行锁 | 表锁 |
| 自增序列 | 不重置 | 重置（从初始值重新开始） |
| 触发器 | 会触发 DELETE 触发器 | 默认不触发触发器 |
| 外键引用 | 有外键引用也能逐行删（受级联规则约束） | 被外键引用时通常不能 TRUNCATE |
| 可回滚 | 可以在事务里 ROLLBACK | 在 PG 里也能回滚，但语义上是"快速清空" |

**记忆法：** `DELETE` 是"一行一行地扔垃圾"，慢但精细；`TRUNCATE` 是"把整个垃圾桶倒了"，快但粗暴。

# 第八部分：进阶——增删改中的其他要点

## 1. 事务在增删改中的重要性

多条增删改必须作为"一个原子单元"执行时，要用事务包起来。最经典的例子是银行转账：A 给 B 转 100 元，要扣 A 的、加 B 的，两步要么都成功要么都失败：

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE name = 'A';
UPDATE accounts SET balance = balance + 100 WHERE name = 'B';
COMMIT;   -- 没问题就提交
-- ROLLBACK;  -- 发现错了就全部撤销
```

为什么重要：

- **多表级联写入**：注册用户要同时写 users、user_profiles、permissions 三张表，必须事务包起来，否则中途失败会留下半截脏数据。
- **危险操作的后悔药**：手动 UPDATE 生产数据时，先 `BEGIN;`，执行 UPDATE，再 SELECT 看改了哪些行，发现没加 WHERE 全表更新了，立刻 `ROLLBACK;` 救命。

**注意！！！** 很多客户端默认开了"自动提交（Auto-Commit）"，你不写 BEGIN，每条语句背后都自动 BEGIN+COMMIT。要测试事务必须手写 `BEGIN;`。事务也不能开太久——被你 UPDATE/DELETE 的行会加锁，开着事务去吃午饭，别人全被卡死。

## 2. UPDATE 的细节：多列同时更新与子查询

一条 UPDATE 可以同时改多列：

```sql
UPDATE students
SET age = age + 1,
    major = 'CS'
WHERE student_id = 1;
```

**注意！！！** 多列更新是"同时"发生的，右边的表达式看到的都是更新前的值。例如 `SET x = y, y = x` 会把 x 和 y 互换，而不是变成同一个值。

UPDATE 里也可以用子查询：

```sql
UPDATE students
SET avg_score = (
    SELECT AVG(score)
    FROM enrollments
    WHERE enrollments.student_id = students.student_id
)
WHERE is_active = TRUE;
```

## 3. INSERT 的其他形式

```sql
-- 不给任何列，全部用默认值插一行
INSERT INTO students DEFAULT VALUES;
```

## 4. 批量操作的性能考虑

- **批量 INSERT vs 逐条 INSERT**：在一条 `VALUES (...), (...), (...)` 里插多行，远快于循环执行几百条单行 INSERT（减少了网络往返和事务开销）。
- **COPY 命令**：PostgreSQL 的 `COPY` 是最快的批量导入方式，用来从文件大批量灌数据（比 INSERT 快一个数量级），适合数据迁移、初始化。

## 5. 软删除 vs 硬删除的设计模式

- **硬删除**：真的 `DELETE FROM` 把行抹掉，数据找不回来。
- **软删除**：不真删，加一个标记列，把行标记为"已删除"：

  ```sql
  ALTER TABLE students ADD COLUMN is_deleted BOOLEAN NOT NULL DEFAULT FALSE;

  -- "删除"时
  UPDATE students SET is_deleted = TRUE WHERE student_id = 1;

  -- 查询时永远过滤掉
  SELECT * FROM students WHERE is_deleted = FALSE;
  ```

什么时候用软删除：数据需要审计追溯、怕误删、外键关联着不能真删。什么时候用硬删除：临时数据、日志、法规要求彻底删除。
