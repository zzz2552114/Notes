# 模糊匹配与结果排序（LIKE / DISTINCT / ORDER BY / LIMIT）

---

# 第一部分：LIKE 模式匹配

这里一定要和 `SELECT *` 区分——`LIKE` 里的 `%`、`_` 是通配符，不是"所有列"。

## 1. `%` 通配

在 `LIKE` 模式里：

```text
% = 任意长度（可以是 0 个字符）
```

例如：

```sql
WHERE student_name LIKE 'A%'
```

表示：

```text
以 A 开头
```

再举几个：

```sql
WHERE student_name LIKE '%a'      -- 以 a 结尾
WHERE student_name LIKE '%app%'   -- 中间包含 app
```

## 2. `_` 单字符

```text
_ = 任意一个字符
```

例如：

```sql
WHERE student_name LIKE '_a%'
```

表示：

> 第二个字符是 a。

`%` 匹配任意多个，`_` 只匹配恰好一个。这是两者唯一的区别。

## 3. 转义 ESCAPE

如果数据本身真的包含 `%` 或 `_`，你需要告诉数据库"这个 % 不是通配符，是字面量"：

```sql
WHERE code LIKE '100\%' ESCAPE '\'
```

意思：反斜杠后面那个 `%` 当普通字符处理。`ESCAPE '\'` 指定用反斜杠做转义符。

# 第二部分：DISTINCT 去重

例如：

```sql
SELECT age
FROM students;
```

可能出现：

```text
18
18
20
20
21
```

加：

```sql
SELECT DISTINCT age
FROM students;
```

得到：

```text
18
20
21
```

## 注意 1！！！

**`DISTINCT` 写在 `SELECT` 后面，而不是语句末尾。**

```sql
SELECT DISTINCT age FROM students;   -- 对
SELECT age FROM students DISTINCT;   -- 错
```

## 注意 2！！！多列去重

```sql
SELECT DISTINCT major, age
```

去掉的是：

> `(major, age)` 这个**组合**重复的行。

不是分别对 major 和 age 各自去重。也就是说，两行只有 major 相同但 age 不同，都会保留；只有 major 和 age 都一样，才算重复。

# 第三部分：ORDER BY 排序

```sql
SELECT student_name, age
FROM students
ORDER BY age;
```

默认升序。显式写：

```sql
ORDER BY age ASC;
```

降序：

```sql
ORDER BY age DESC;
```

## 1. 多列排序

```sql
ORDER BY age DESC, student_name ASC;
```

意思：

1. 先按 age 从大到小；
2. age 一样的，再按名字升序。

记住：

```text
ORDER BY 是"先排第一关键字，再用第二关键字打破平局"
```

## 2. NULL 参与排序时排在哪里？

还有一个容易被忽略的点：**NULL 参与排序时排在哪里？** 标准 SQL 没有规定死，PostgreSQL 的默认行为是：

```text
ASC  → NULL 排在最后
DESC → NULL 排在最前
```

如果你希望明确控制，可以写：

```sql
ORDER BY age DESC NULLS LAST
```

或者：

```sql
ORDER BY age ASC NULLS FIRST
```

`NULLS FIRST / NULLS LAST` 是显式表达意图的好习惯。后面的综合统计题里，平均成绩可能是 NULL，就需要注意这一点。

## 3. 为什么 ORDER BY 经常可以用 SELECT 别名？

因为逻辑上：

```text
SELECT 先于 ORDER BY
```

所以：

```sql
SELECT
    age + 1 AS next_age
FROM students
ORDER BY next_age;
```

是自然的——SELECT 阶段已经把 `next_age` 这个别名造出来了，ORDER BY 在后面就能用它。这正好和 WHERE 不能用别名形成对照。

# 第四部分：LIMIT 和 OFFSET

PostgreSQL 中常用：

```sql
LIMIT 10
OFFSET 20
```

注意：`LIMIT` 是 PostgreSQL 等数据库里很常见的写法，但它不是标准 SQL 最核心的可移植写法。

意思：

> 先 OFFSET 跳过前 20 行，再 LIMIT 取最多 10 行。

它和分页有关。

## 注意！！！

如果没有 `ORDER BY`，你不能把分页结果理解成稳定的"第 1 页、第 2 页"。所以通常：

```sql
ORDER BY student_id
LIMIT 10 OFFSET 20;
```

比单独：

```sql
LIMIT 10 OFFSET 20
```

更可靠。**LIMIT/OFFSET 必须配合 ORDER BY**，否则每次翻页的顺序都可能不一样，同一条记录会在页与页之间乱跳。

# 第五部分：进阶——更多模糊匹配

## 1. ILIKE（PostgreSQL 不区分大小写匹配）

`LIKE 'abc%'` 是严格区分大小写的。如果在 MySQL 里想忽略大小写，常常要改排序规则。在 PG 里，直接用 `ILIKE`：

```sql
WHERE student_name ILIKE '%alice%'
```

就能找出 'Alice'、'ALICE'、'alice'，非常实用。它就是"忽略大小写的 LIKE"。

## 2. ~ 和 ~*（PostgreSQL 正则匹配运算符）

PostgreSQL 内置了正则表达式匹配运算符：

| 运算符 | 含义 |
|---|---|
| `~` | 匹配正则，区分大小写 |
| `~*` | 匹配正则，不区分大小写 |
| `!~` | 不匹配正则，区分大小写 |
| `!~*` | 不匹配正则，不区分大小写 |

例子：

```sql
-- 邮箱必须符合 xxx@xxx.xxx 格式
WHERE email ~ '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$';

-- 名字以 a 开头（忽略大小写）
WHERE student_name ~* '^a';
```

正则比 LIKE 强大得多，但也难写，需要正则基础。

## 3. SIMILAR TO（SQL 标准正则）

SQL 标准也有一个正则谓词 `SIMILAR TO`，介于 LIKE 和完整正则之间：

```sql
WHERE student_name SIMILAR TO 'A%';
```

它用 `%` 和 `_`（同 LIKE），但支持 `|`（或）、`()`（分组）。实际用得少，知道即可。

# 第六部分：进阶——排序的更多玩法

## 1. ORDER BY 中的表达式排序

可以按计算结果排序：

```sql
SELECT student_name, score * 1.1 AS bonus
FROM enrollments
ORDER BY score * 1.1 DESC;
```

## 2. ORDER BY 按列序号排序

可以用列在 SELECT 里的位置编号排序：

```sql
SELECT student_name, age, major
FROM students
ORDER BY 2 DESC;    -- 按第二列 age 排序
```

**注意！！！** 这种写法短但脆弱——SELECT 列顺序一改，排序就跟着变，还降低可读性。生产环境不推荐。

## 3. LIMIT ... WITH TIES（PostgreSQL 特有）

如果你想取"成绩最高的前 3 名"，但第 3 名有并列，`LIMIT 3` 只会随机保留一个。`WITH TIES` 会把并列的都带上：

```sql
SELECT student_name, score
FROM enrollments
ORDER BY score DESC
LIMIT 3 WITH TIES;
```

如果第 3 名有两个人同分，两条都会返回。

## 4. 排序的稳定性

"稳定排序"指：当两行排序键相同时，它们的相对顺序在多次查询里保持不变。没有唯一的第二排序键时，数据库不保证稳定。所以做精确分页时，务必加一个唯一的决胜列（如主键）：

```sql
ORDER BY score DESC, student_id ASC
```

# 第七部分：进阶——分页的性能与 keyset pagination

## 1. LIMIT/OFFSET 的深分页陷阱

`LIMIT 10 OFFSET 100000` 很慢。原因：数据库不是"直接跳到第 100000 行"，而是**把前面 100010 行都扫出来，再扔掉前 100000 个**。OFFSET 越大，白白扫过的行越多，越慢。这就是"深分页陷阱"。

## 2. keyset pagination（游标分页 / seek pagination）

替代 OFFSET 的高性能方案：记住上一页最后一条的排序键，下次从它后面接着取：

```sql
-- 第一页
SELECT student_id, student_name, score
FROM enrollments
ORDER BY score DESC, student_id
LIMIT 10;

-- 第二页：记住上一页最后一条 score=88, student_id=5
SELECT student_id, student_name, score
FROM enrollments
WHERE score < 88 OR (score = 88 AND student_id > 5)
ORDER BY score DESC, student_id
LIMIT 10;
```

这样数据库直接从"上次断的地方"开始，每一页都很快，和翻到第几页无关。适合大数据量、APP 无限滚动加载。

| 对比 | OFFSET 分页 | keyset 分页 |
|---|---|---|
| 实现 | 简单 | 稍复杂 |
| 深翻页性能 | 越来越慢 | 始终很快 |
| 能否跳页 | 能跳到任意页 | 只能顺序往后翻 |

# 第八部分：进阶——DISTINCT 的补充

## 1. DISTINCT 与 GROUP BY 的关系

`SELECT DISTINCT major FROM students` 和 `SELECT major FROM students GROUP BY major` 结果几乎等价——都是对 major 去重。区别是 GROUP BY 还能做聚合计算，DISTINCT 只去重。

## 2. DISTINCT 与 NULL 的关系

`DISTINCT` 把多个 NULL 视为"相等"，所以全表如果有一堆 NULL 的 major，去重后只保留一个 NULL。这和三值逻辑里"NULL=NULL 是 UNKNOWN"看似矛盾，但在 DISTINCT/分组语境下，数据库把 NULL 归为同一组。

## 3. DISTINCT ON（PostgreSQL 特有，与排序配合）

前面 SELECT 文档提过，这里重点讲它和排序的配合：`DISTINCT ON` 取每组第一行，**必须靠 ORDER BY 决定"谁是第一行"**：

```sql
-- 每个学生取最近一次选课记录
SELECT DISTINCT ON (student_id)
    student_id, course_id, enrolled_at
FROM enrollments
ORDER BY student_id, enrolled_at DESC;
```

## 4. 集合运算中的 ORDER BY

用 `UNION`/`INTERSECT`/`EXCEPT` 把多个结果拼起来时，`ORDER BY` 只能写在**整个语句的最后**，对最终合并结果排序，不能给中间某个 SELECT 单独排。
