# 建表与数据定义（CREATE TABLE / ALTER TABLE）

---

# 第一部分：贯穿项目——同一个"大学选课数据库"

后面的练习不再"一学一个语法就换一张新表"。从现在开始一直使用三张核心表：

```text
students
courses
enrollments
```

它们代表：

```text
students      学生
courses       课程
enrollments   学生与课程之间的选课关系
```

关系：

```text
students 1 ─── N enrollments N ─── 1 courses
```

意思是：一个学生可以选多门课，一门课可以被多个学生选，`enrollments` 就是连接这两张表的"桥"（中间表）。

你会不断在这三张表上增加操作能力：

```text
建结构 → 插数据 → 查数据 → 改数据 → 删数据 → 连表
      → 分组统计 → 子查询 → 集合运算 → 事务 → 综合查询
```

# 第二部分：建表 CREATE TABLE

建表就是把"这张表长什么样"写下来，交给数据库保存。骨架是：

```sql
CREATE TABLE 表名 (
    列名 类型 约束,
    列名 类型 约束,
    ...
    表级约束
);
```

例如（本项目的 students 表完整版）：

```sql
CREATE TABLE students (
    student_id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    student_name VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL UNIQUE,
    age INTEGER CHECK (age >= 0),
    major VARCHAR(50),
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

拆开看，每一列都是"列名 + 类型 + 约束"：

```text
student_id   INTEGER   GENERATED ALWAYS AS IDENTITY   PRIMARY KEY
└─ 列名       └─ 类型    └─ 自动生成编号               └─ 主键
student_name VARCHAR(50) NOT NULL
└─ 列名       └─ 类型     └─ 不允许为空
```

`CREATE TABLE` 这个名字也说明了 SQL 的一种习惯：`CREATE` 负责"造出一个新对象"，后面跟对象的种类——`DATABASE` / `TABLE` / `INDEX` / `VIEW`。所以以后看到 `CREATE INDEX`、`CREATE VIEW`，不用重新记一套动词，只要看 `CREATE` 后面是谁。

## 1. PRIMARY KEY（主键）

```sql
student_id INTEGER PRIMARY KEY
```

主键的核心是：

```text
唯一
非 NULL
用来标识一行
```

一个表可以有多个 `UNIQUE` 列，但通常只有一个主键，因为主键回答的是"这行到底是谁"。数据库会自动为主键建立唯一索引，并且主键列隐式 `NOT NULL`。

## 2. UNIQUE（唯一）

```sql
email VARCHAR(100) UNIQUE
```

不允许重复。

```text
PRIMARY KEY 是"这行是谁"
UNIQUE      是"这个值不能重复"
```

**注意！！！** `UNIQUE` 和 `PRIMARY KEY` 的关键区别：

| 对比 | PRIMARY KEY | UNIQUE |
|---|---|---|
| 能否为 NULL | 不能 | 可以（除非再写 NOT NULL） |
| 一个表能有几个 | 通常一个 | 可以有多个 |
| 是否自动建索引 | 是 | 是 |

## 3. NOT NULL（不能为空）

```sql
student_name VARCHAR(50) NOT NULL
```

不允许缺失。如果插入时不给这一列值，数据库直接报错。

## 4. DEFAULT（默认值）

```sql
created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
```

如果插入时没提供 `created_at`，数据库自己给默认值。`CURRENT_TIMESTAMP` 就是"现在"，所以插入数据时不用手动填时间。

## 5. CHECK（检查条件）

```sql
CHECK (age >= 0)
```

告诉数据库：

> 不允许年龄为负数。

`CHECK` 的作用是把"业务上显然荒唐的值"挡在数据库门口，而不是让它散落在应用程序的各个 `if` 里。

### 什么样的约束应该放到 CHECK 里？

没有"某类约束必须写 `CHECK`"这种绝对说法。更准确地说：

> 那些**没有专门约束语法**、又需要用布尔条件限制数据的约束，通常只能用 `CHECK` 表达。

主键、唯一、非空、外键都有专门关键字，剩下的业务规则（年龄不能负、成绩 0~100、状态只能是某几个值）就用 CHECK。

括号里必须是一个**布尔表达式 / 条件**，比如：

```sql
CHECK (age >= 0)
CHECK (status IN ('active', 'inactive'))
CHECK (end_date > start_date)
CHECK (id IS NOT NULL)
```

**注意！！！** CHECK 后面必须加括号 `CHECK (...)`，这是它和 WHERE 最大的形式区别（WHERE 不用加括号）。

## 6. 自增主键：GENERATED ALWAYS AS IDENTITY

```sql
student_id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

它表示：

> 这一列的值由数据库自己生成，不要你手填。

`GENERATED ... AS IDENTITY` 是标准 SQL 的写法。PostgreSQL 里你还可能看到更老的写法：

```sql
student_id SERIAL PRIMARY KEY
```

`SERIAL` 是 PostgreSQL 的历史习惯写法，能少打几个字，但它不是标准 SQL。初学阶段建议先记住 `GENERATED ... AS IDENTITY`，看到 `SERIAL` 知道"它是自增"即可。

## 7. FOREIGN KEY（外键）与 REFERENCES

外键可以写在列定义里（列级外键），也可以写在表末尾（表级外键）。

先建被引用的表 `students`（父表）：

```sql
CREATE TABLE students (
    student_id INT PRIMARY KEY,
    name VARCHAR(50) NOT NULL
);
```

然后建子表 `enrollments`，用**表级外键**：

```sql
CREATE TABLE enrollments (
    enrollment_id INT PRIMARY KEY,
    student_id INT NOT NULL,
    course_name VARCHAR(50),
    FOREIGN KEY (student_id)
        REFERENCES students(student_id)
);
```

这里：

- `enrollments` 是子表；
- `students` 是父表；
- `FOREIGN KEY (student_id)` 里的 `student_id` 是 `enrollments` 表的列；
- `REFERENCES students(student_id)` 表示引用 `students` 表的 `student_id` 列。

### 也可以写在列定义里（列级外键）

```sql
CREATE TABLE enrollments (
    enrollment_id INT PRIMARY KEY,
    student_id INT NOT NULL REFERENCES students(student_id),
    course_name VARCHAR(50)
);
```

这里：

```sql
student_id INT NOT NULL REFERENCES students(student_id)
```

就等价于在表末尾写：

```sql
FOREIGN KEY (student_id) REFERENCES students(student_id)
```

只不过列级写法更紧凑，适合单列外键。

意思：

> enrollments.student_id 必须引用 students 中真实存在的 student_id。

`REFERENCES` 这个词很形象：它不复制学生数据，只是"指向" students 里的某一行。这正是关系数据库"用键把表连起来"的体现——数据只存一份，其他表引用它。

外键默认要求被引用的值必须存在，所以你不能先往 enrollments 里插一个不存在的 student_id。这是数据库在替你维护三张表之间的一致性。

### 注意！！！！

外键约束的规则是：

> 如果外键列的值不是 NULL，那么它必须能在被引用表的主键/唯一键中找到；
> 如果外键列的值是 NULL，就表示"没有引用任何行"，约束自动通过。

所以：

- 被引用表的主键或 UNIQUE 键：不能 NULL。
- 引用表的外键列：默认可以 NULL，除非你写 `NOT NULL`。

## 8. 组合主键

有时单独一列不够充当主键，比如选课表：

```sql
PRIMARY KEY (student_id, course_id)
```

它表示：

```text
(student_id, course_id) 这个组合不能重复
```

也就是同一个学生不能把同一门课选两次，但一个学生可以选很多门课，一门课也可以被很多人选。组合主键是写在表级约束位置的。

# 第三部分：ALTER TABLE（改表结构）

在数据库运行了一年之后，业务发展了，原本设计的表结构不再满足需求（比如需要给用户增加一个"微信号"字段，或者把"姓名"列加长）。`ALTER TABLE` 允许你在**不删除原表、不丢失数据**的情况下，动态修改表的结构。

如果没有它，你需要：创建一个新表 → 把旧表几百万条数据导出来 → 转换格式 → 塞进新表 → 删掉旧表。不仅速度慢，还要停机维护。`ALTER TABLE` 让你可以像给飞行的飞机换引擎一样修改结构。

## 1. 常用语法

```sql
-- 增加一列
ALTER TABLE 表名 ADD COLUMN 列名 数据类型;

-- 删除一列
ALTER TABLE 表名 DROP COLUMN 列名;

-- 修改列的数据类型
ALTER TABLE 表名 ALTER COLUMN 列名 TYPE 新数据类型;

-- 增加一个约束 (例如唯一约束)
ALTER TABLE 表名 ADD CONSTRAINT 约束名 UNIQUE(列名);
```

例子：

```sql
-- 假设有个 orders 表，我想加个备注字段
ALTER TABLE orders ADD COLUMN remarks VARCHAR(200);

-- 把金额的数据类型从 INTEGER 扩大到 NUMERIC(10,2) 以支持小数
ALTER TABLE orders ALTER COLUMN amount TYPE NUMERIC(10,2);
```

常见用法：

- **业务迭代扩充**：最常见的就是 `ADD COLUMN`。
- **数据清洗善后**：早期的 `phone` 字段随便大家填，后来清洗完脏数据后，通过 `ALTER TABLE ... ADD CONSTRAINT` 强制加上 `CHECK` 规则。

## 2. 重要注意事项

**注意！！！**

- **带默认值的新增列可能很慢**：在较老的数据库版本中，如果你新增一列且指定了 `DEFAULT 'xxx'`，数据库会强行把全表百万行数据全部重写一遍塞入这个默认值，这会导致整张表被长时间锁死。不过 PostgreSQL 11 之后优化了这点，带常量默认值的添加几乎是瞬间完成的。
- **DROP COLUMN 的不可逆转**：删除列会导致该列数据永久丢失。它只是"标记为删除"，空间未必立刻还给操作系统，但数据你再也查不到了。
- **修改类型可能失败**：如果你要把 `VARCHAR` 转成 `INTEGER`，但这一列里已经有一些存了 `'abc'` 的脏数据，那么 `ALTER COLUMN TYPE` 会直接报错阻止你。你需要结合 `USING` 子句来指明转换规则。

# 第四部分：进阶——约束与外键的深入

## 1. 表级约束 vs 列级约束

| 对比 | 列级约束 | 表级约束 |
|---|---|---|
| 写法位置 | 跟在某一列定义后面 | 写在所有列定义之后 |
| 能约束几列 | 只能约束当前这一列 | 可以约束多列 |
| 例子 | `email VARCHAR(100) UNIQUE` | `UNIQUE(col_a, col_b)` |
| 适合 | 单列的 NOT NULL / UNIQUE / CHECK | 组合主键、组合唯一、多列 CHECK、外键 |

多列联合约束必须写在表级。例如"起止日期必须合法"要同时引用两列，只能写表级：

```sql
CREATE TABLE courses (
    course_id INT PRIMARY KEY,
    start_date DATE,
    end_date DATE,
    CHECK (end_date > start_date)
);
```

## 2. 约束命名的最佳实践

你可以不给约束起名，数据库会自动生成一个名字（类似 `students_email_key`）。但给约束起有意义的名字，在报错时能一眼看懂是哪条规则拦了你：

```sql
ALTER TABLE students
    ADD CONSTRAINT check_age_nonnegative CHECK (age >= 0);

ALTER TABLE students
    ADD CONSTRAINT uq_students_email UNIQUE (email);
```

**最佳实践命名法：** `约束类型_表名_列名`，例如 `check_age_nonnegative`、`uq_students_email`、`fk_enrollments_student`。这样报错信息 `violates check constraint "check_age_nonnegative"` 你一看就懂。

## 3. CHECK 约束的高级用法

### 多列联合 CHECK

```sql
CHECK (score IS NULL OR score BETWEEN 0 AND 100)
CHECK (end_date > start_date)
CHECK (status = 'graduated' OR graduate_date IS NOT NULL)
```

### CHECK 与 NULL 的交互

还记得三值逻辑吗？`CHECK` 只在结果为 FALSE 时拒绝。所以：

```sql
CHECK (age >= 0)
```

允许 `age` 为 NULL（因为 `NULL >= 0` 是 UNKNOWN，CHECK 放过）。如果你想强制 age 既非空又非负，要写：

```sql
age INTEGER NOT NULL CHECK (age >= 0)
```

### CHECK 里使用函数

```sql
CHECK (LENGTH(phone) >= 8)
CHECK (email LIKE '%@%.%')
```

## 4. 外键级联操作详解

默认情况下，如果你试图删除一个"还被子表引用着"的学生，数据库会报错拒绝（因为那会留下孤儿选课记录）。但有时你希望"删学生时自动删掉他的选课"，这就需要级联动作。写在 `REFERENCES` 后面：

```sql
FOREIGN KEY (student_id)
    REFERENCES students(student_id)
    ON DELETE CASCADE
```

各种级联行为对比：

| 行为 | 父行被删除时，子表怎么办 | 示例场景 |
|---|---|---|
| `NO ACTION`（默认） | 报错，拒绝删除 | 最安全，默认值 |
| `RESTRICT` | 报错，拒绝删除（检查更早） | 同 NO ACTION，时机略不同 |
| `CASCADE` | 自动删掉所有引用它的子行 | 删学生时自动删其选课 |
| `SET NULL` | 把子表外键列置为 NULL | 删部门时，员工的部门变空 |
| `SET DEFAULT` | 把子表外键列设为默认值 | 较少用 |

例子：

```sql
-- 删学生，自动删他的所有选课记录
CREATE TABLE enrollments (
    enrollment_id INT PRIMARY KEY,
    student_id INT NOT NULL
        REFERENCES students(student_id) ON DELETE CASCADE,
    course_id INT NOT NULL
        REFERENCES courses(course_id) ON DELETE CASCADE
);

-- 删部门，员工的 department_id 变成 NULL
CREATE TABLE employees (
    emp_id INT PRIMARY KEY,
    name VARCHAR(50),
    department_id INT REFERENCES departments(dept_id) ON DELETE SET NULL
);
```

**注意！！！** `ON DELETE CASCADE` 很方便但很危险——一条 `DELETE FROM students WHERE ...` 可能悄悄删掉成千上万条选课记录。用之前务必想清楚"这个级联是不是我真想要的"。

## 5. 约束的延迟校验（DEFERRABLE）

默认外键在每条语句结束时立即校验。但有个经典死锁场景：表 A 引用表 B，表 B 又引用表 A，你插入时无论先插哪边都会违反外键。这时可以把约束设为"可延迟"，到事务提交时才统一校验：

```sql
CREATE TABLE enrollments (
    ...
    student_id INT REFERENCES students(student_id)
        DEFERRABLE INITIALLY DEFERRED
);
```

- `INITIALLY IMMEDIATE`（默认）：每条语句后立即检查。
- `INITIALLY DEFERRED`：事务提交时才检查。

这是进阶内容，初学知道有这回事即可。

# 第五部分：进阶——自增主键的多种方式

这是建表时最容易困惑的点。四种方式对比：

| 方式 | 是否标准 SQL | 原理 | 优缺点 |
|---|---|---|---|
| `SERIAL` | 否（PG 历史写法） | 背后自动建一个 SEQUENCE，列默认值取序列下一个值 | 少打字，但不是标准，序列和列解耦不彻底 |
| `GENERATED ALWAYS AS IDENTITY` | 是（SQL 标准） | 标准标识列 | 最规范，禁止手动插入值，最安全 |
| `GENERATED BY DEFAULT AS IDENTITY` | 是 | 标准标识列，但允许你手动覆盖插入值 | 迁移数据时方便 |
| `SEQUENCE`（手动） | 是 | 自己 `CREATE SEQUENCE`，列默认 `NEXTVAL` | 最灵活，可多表共享一个序列 |

例子：

```sql
-- 方式1：老写法 SERIAL
CREATE TABLE t1 (id SERIAL PRIMARY KEY);

-- 方式2：标准、最安全（推荐初学）
CREATE TABLE t2 (
    id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY
);

-- 方式3：允许手动指定 id
CREATE TABLE t3 (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
);

-- 方式4：手动序列
CREATE SEQUENCE my_seq START 100;
CREATE TABLE t4 (id INTEGER PRIMARY KEY DEFAULT NEXTVAL('my_seq'));
```

**记忆法：** `ALWAYS` 表示"数据库永远替你生成，你别手填"；`BY DEFAULT` 表示"你不填我才生成，你填了我也不拦"。初学用 `GENERATED ALWAYS AS IDENTITY` 最规范。

# 第六部分：进阶——更多建表与改表能力

## 1. CREATE TABLE IF NOT EXISTS

表不存在时才建，存在就跳过（常用于脚本重复执行不报错）：

```sql
CREATE TABLE IF NOT EXISTS students (...);
```

## 2. CREATE TABLE AS（CTAS，把查询结果建成新表）

```sql
CREATE TABLE students_cs AS
SELECT * FROM students WHERE major = 'CS';
```

它会按 SELECT 结果的列和数据直接生成一张新表，非常适合做数据快照、备份、中间结果落盘。**注意：CTAS 不会复制原表的主键、约束、索引，只复制列结构和数据。**

## 3. 临时表（TEMP / TEMPORARY TABLE）

只在当前会话/事务里存在，结束自动删除，适合存中间结果：

```sql
CREATE TEMP TABLE tmp_pass (
    student_id INT,
    avg_score NUMERIC
);
```

## 4. UNLOGGED TABLE（不记日志的表）

普通表的每一次修改都会写 WAL（预写日志）以保证崩溃可恢复。`UNLOGGED` 表不写日志，插入飞快，但数据库崩溃后数据会丢。适合存可重建的中间数据：

```sql
CREATE UNLOGGED TABLE fast_cache (...);
```

## 5. ALTER TABLE 的更多操作

```sql
-- 改默认值
ALTER TABLE students ALTER COLUMN is_active SET DEFAULT FALSE;
ALTER TABLE students ALTER COLUMN is_active DROP DEFAULT;

-- 改是否允许 NULL
ALTER TABLE students ALTER COLUMN major SET NOT NULL;   -- 前提是现有数据没有 NULL
ALTER TABLE students ALTER COLUMN major DROP NOT NULL;

-- 重命名列
ALTER TABLE students RENAME COLUMN age TO birth_year;

-- 重命名表
ALTER TABLE students RENAME TO students_backup;

-- 移动到别的 schema
ALTER TABLE students SET SCHEMA archive;
```

## 6. ALTER COLUMN TYPE 的 USING 子句

改类型时，如果数据库无法自动转换，要用 `USING` 告诉它怎么转：

```sql
-- 把字符串列转成整数，并清洗脏数据
ALTER TABLE orders
    ALTER COLUMN amount TYPE INTEGER
    USING CASE
        WHEN amount ~ '^[0-9]+$' THEN amount::INTEGER
        ELSE 0
    END;
```

`USING` 后面是一个表达式，描述"老值怎么算成新值"。这是处理"历史脏数据 + 改类型"的唯一手段。

# 第七部分：进阶——自定义数据类型

## 1. 枚举类型 ENUM

当一列只能取某几个固定值时，除了 `CHECK (status IN (...))`，还可以建枚举类型：

```sql
CREATE TYPE student_status AS ENUM ('active', 'inactive', 'graduated');

CREATE TABLE students (
    ...
    status student_status
);
```

**ENUM vs CHECK 对比：**

| 对比 | ENUM | CHECK |
|---|---|---|
| 取值集合 | 独立类型，可多表复用 | 绑死在一张表上 |
| 加新值 | `ALTER TYPE ... ADD VALUE` | 改 CHECK 表达式 |
| 存储 | 内部用序号，省空间 | 普通字符串 |
| 灵活性 | 较低 | 高 |

## 2. 域 DOMAIN

域是"带约束的自定义类型"，把一组常用约束打包复用：

```sql
CREATE DOMAIN positive_int AS INTEGER
    CHECK (VALUE > 0);

CREATE TABLE courses (
    credits positive_int    -- 这一列自动具备 > 0 的约束
);
```

`VALUE` 代表这一列当前的值。域适合把"非负整数""合法邮箱"这类反复出现的约束抽成一个类型。
