# 集合运算：UNION / INTERSECT / EXCEPT

SQL 不只有 JOIN。还有集合运算（Set Operations），它们将多个查询的"结果集"当作集合进行合并或相减：

```text
UNION      并集（去重）
UNION ALL  并集（不去重）
INTERSECT  交集
EXCEPT     差集
```

它们的核心区别于 JOIN：

- **JOIN** 主要是**左右横向**拼接数据（增加列，扩展信息）。
- **集合运算** 主要是**上下纵向**堆叠数据（增加行，合并结果）。

```text
JOIN:    (a, b) + (c, d) → (a, b, c, d)   横向加列
集合运算: (a, b)          → (a, b)           纵向加行
          (c, d)            (c, d)
```

使用集合运算的**严格前提条件**：

1. **列数必须完全一致**：两个 SELECT 返回的字段数量必须相同。
2. **对应列的数据类型必须兼容**：第一列对第一列，第二列对第二列，类型必须能隐式转换（最好是完全一样）。
3. **最终列名**：结果集的列名通常由第一个 SELECT 语句决定。

> 注意！！！这三个条件缺一不可。列数对不上、对应列类型不兼容，数据库直接报错。别想着"左边查 3 列、右边查 4 列"还能拼起来——集合运算只做"同结构结果集的纵向堆叠"。

---

## 一、UNION 与 UNION ALL（并集）

**作用**：将两个查询的结果合并到一起。

- `UNION`：合并后会**自动去除重复行**。
- `UNION ALL`：合并后**保留所有重复行**。

**常用情境**：

- 需要从多个结构相似的表中汇总数据（比如今年的订单表 `orders_2023` 和去年的订单表 `orders_2022` 汇总）。
- 当一个非常复杂的 `OR` 逻辑导致索引失效或者难以阅读时，可以拆分成两个单独的 `SELECT` 再 `UNION` 起来。

**注意事项**：

- `UNION` 在后台需要进行一次全局去重（通常是通过排序或哈希），非常耗费性能。
- **最佳实践**：如果你在逻辑上能确定两个结果集肯定没有交集，或者你不在乎重复数据，**请永远优先使用 `UNION ALL`**。只有当你明确需要去重时，才使用 `UNION`。

**示例**：

```sql
SELECT student_name FROM students WHERE major = 'CS'
UNION
SELECT student_name FROM students WHERE age >= 20;
```

如果有一个学生既是 CS 专业，年龄又 >= 20，`UNION` 会保证名字只出现一次。如果你用 `UNION ALL`，这个名字就会出现两次。

---

## 二、INTERSECT（交集）

**作用**：提取两个查询结果中**都存在**的行。也就是"取共同点"。

**常用情境**：

- 寻找同时满足两个复杂条件的数据集合。
- 比较两个表的数据差异，找出共同拥有的人或记录（例如：购买了商品 A 且同时购买了商品 B 的用户）。

**注意事项**：

- 很多时候 `INTERSECT` 可以被 `INNER JOIN` 或 `EXISTS` 子查询替代。但是当你要比较整个结果集的多列内容时，`INTERSECT` 写起来更直观。
- `INTERSECT` 也会自动去重。

**示例**：

```sql
-- 既是 CS 专业，又是年龄 >= 20 的学生
SELECT student_name FROM students WHERE major = 'CS'
INTERSECT
SELECT student_name FROM students WHERE age >= 20;
```

---

## 三、EXCEPT（差集）

> *注：在 Oracle 等一些数据库中，EXCEPT 被称为 MINUS。在 PostgreSQL 和 SQL Server 中使用 EXCEPT。*

**作用**：从第一个查询结果中，**减去**第二个查询结果中也存在的行。即"只在左边，不在右边"。

**常用情境**：

- 找出某种"缺失"：比如所有学生减去已经选课的学生，剩下的就是没选课的学生。
- 排除特定条件的数据：查询某类群体，但要从中剔除掉另一个复杂查询算出来的群体。

**注意事项**：

- `EXCEPT` 是有**方向性**的。`A EXCEPT B` 和 `B EXCEPT A` 的结果完全不同。
- `EXCEPT` 也可以用 `LEFT JOIN ... WHERE right_table.id IS NULL` 或 `NOT EXISTS` 替代，但在表达"全表差异"时 `EXCEPT` 非常直观。

**示例**：

```sql
-- 所有 CS 学生，排除掉年龄大于 21 岁的，剩下的 CS 学生
SELECT student_name FROM students WHERE major = 'CS'
EXCEPT
SELECT student_name FROM students WHERE age > 21;
```

## 四、集合运算与 ORDER BY / LIMIT

如果要对集合运算后的最终结果进行排序或限制数量，`ORDER BY` 和 `LIMIT` 只能写在**整个语句的最后面**，并且排序的字段名必须是第一个 `SELECT` 中输出的字段名。

```sql
SELECT student_name, age FROM students WHERE major = 'CS'
UNION
SELECT student_name, age FROM students WHERE major = 'Math'
ORDER BY age DESC -- 对合并后的结果排序
LIMIT 5;          -- 从合并结果中取前5个
```

*(注意：不能在第一个 SELECT 后面单独加 ORDER BY，除非用括号包起来当子查询使用。)*

> 注意！！！为什么 ORDER BY 只能写在最后？因为集合运算的中间结果是"纵向堆叠"出来的，你没法对"堆到一半"的东西排序。要排序，就对**最终合并结果**排序。排序字段名用第一个 SELECT 的列名（因为最终列名由第一个 SELECT 决定）。

## 五、集合运算的性能对比（进阶）

| 运算 | 是否去重 | 性能成本 |
|---|---|---|
| `UNION ALL` | 不去重 | 最低，纯粹纵向堆叠 |
| `UNION` | 去重 | 高，要全局排序/哈希去重 |
| `INTERSECT` | 去重 | 高，要算交集并去重 |
| `EXCEPT` | 去重 | 高，要算差集并去重 |

核心结论：**去重是有成本的**。`UNION ALL` 几乎只是"把两段结果拼起来"，而 `UNION` 要额外做一次全局去重（排序或哈希），数据量大时这个成本很可观。

---

## 六、UNION ALL 优先原则的详细论证

什么时候可以放心用 `UNION ALL`？

1. **逻辑上确定两个结果集没有交集**：比如 `orders_2023` 和 `orders_2024` 是按年份分表的，本来就不会有重复行，用 `UNION` 纯属浪费。
2. **重复数据不影响业务逻辑**：你只是要把两类记录都列出来，重复一行两行无所谓。
3. **性能收益**：省掉一次全局去重，大数据量下可能快好几倍。

反过来，只有当你**明确需要"每个行只出现一次"**时，才用 `UNION`。

> 记忆法：默认写 `UNION ALL`，想到"要去重"了再改成 `UNION`。而不是默认 `UNION`，"嫌慢了"才改 `UNION ALL`——大多数人搞反了方向。

## 七、集合运算与 JOIN 的等价转换（进阶）

| 集合运算 | 等价写法 | 区别 |
|---|---|---|
| `INTERSECT` | `INNER JOIN` | INTERSECT 自动去重，INNER JOIN 不去重 |
| `EXCEPT` | `LEFT JOIN ... WHERE 右表.id IS NULL` 或 `NOT EXISTS` | EXCEPT 自动去重 |
| `UNION ALL` | 多个分支纵向拼 | — |

举例："选了课程 1 又选了课程 3 的学生"：

```sql
-- 用 INTERSECT
SELECT student_id FROM enrollments WHERE course_id = 1
INTERSECT
SELECT student_id FROM enrollments WHERE course_id = 3;

-- 等价于 INNER JOIN / EXISTS
SELECT a.student_id
FROM enrollments a
JOIN enrollments b ON a.student_id = b.student_id
WHERE a.course_id = 1 AND b.course_id = 3;
```

> 注意！！！区别在于**去重**：INTERSECT 会自动去重，而 INNER JOIN 如果一个学生满足多次会输出多行。要和 INTERSECT 完全等价，INNER JOIN 后面还得加 `DISTINCT`。

## 八、INTERSECT ALL / EXCEPT ALL（保留重复行，进阶）

普通 `INTERSECT` / `EXCEPT` 会去重。而 `INTERSECT ALL` / `EXCEPT ALL` 是**基于多重集**的运算，保留重复次数。

举例：结果 A 里张三出现 3 次，结果 B 里张三出现 1 次。

- `A INTERSECT B`：张三出现 **1 次**（去重后）。
- `A INTERSECT ALL`：张三出现 **1 次**（取两边次数的较小值 min(3,1)=1）。

再比如 A 里张三 3 次、B 里张三 2 次：

- `A EXCEPT B`：张三 **0 次**（只要出现过就减去）。
- `A EXCEPT ALL`：张三 **1 次**（减去 2 次，剩 3-2=1）。

> 注意！！！`INTERSECT ALL` / `EXCEPT ALL` 在 MySQL 里不支持，PostgreSQL 支持。日常用得少，但理解"去重 vs 保留重复"的差别很重要。

## 九、集合运算中的 NULL 处理（进阶）

一个反直觉但重要的规则：**在集合运算中，NULL 被视为相等**（两个 NULL 算"重复行"）。

这和 WHERE 里不一样——WHERE 里 `NULL = NULL` 是 UNKNOWN。但在 `UNION` 去重时，两行"所有列都是 NULL"会被认为是同一行，`UNION` 会合并它们。

```sql
SELECT NULL AS a
UNION
SELECT NULL AS a;
```

结果只有一行（NULL），而不是两行。因为集合运算把 NULL=NULL 当相等来去重。

> 记忆法：**比较（WHERE）里 NULL≠NULL，但集合去重里 NULL=NULL。** 规则是为不同目的设计的，别混。

## 十、括号控制运算优先级（进阶）

当多个集合运算混在一起时，有个默认优先级：**`INTERSECT` 的优先级高于 `UNION` 和 `EXCEPT`**。

也就是说：

```sql
A UNION B INTERSECT C
```

会被先算 `B INTERSECT C`，再算 `A UNION (...)`，而不是从左到右。

这很容易出错。**最佳实践：用括号明确指定顺序**，别依赖默认优先级：

```sql
(A UNION B) INTERSECT C
-- 或
A UNION (B INTERSECT C)
```

> 注意！！！只要你写了不止一种集合运算，就加括号。靠记优先级迟早踩坑，括号零成本。

## 十一、数据对比经典模式（进阶）

集合运算最经典的用途之一是**对比两张表的数据差异**——找出"在 A 不在 B"和"在 B 不在 A"的行：

```sql
-- A 有而 B 没有
SELECT * FROM table_a
EXCEPT
SELECT * FROM table_b

UNION ALL

-- B 有而 A 没有
SELECT * FROM table_b
EXCEPT
SELECT * FROM table_a;
```

这个 `A EXCEPT B UNION ALL B EXCEPT A` 的组合，就是两张表的"对称差"——所有两边不一致的行都列出来。做数据迁移、数据校验时非常常用。

## 十二、各数据库支持差异（进阶）

| 运算 | PostgreSQL | MySQL | Oracle | SQL Server |
|---|---|---|---|---|
| UNION / UNION ALL | ✅ | ✅ | ✅ | ✅ |
| INTERSECT | ✅ | ❌（8.0 前不支持） | ✅ | ✅ |
| EXCEPT | ✅ | ❌ | 叫 `MINUS` | ✅ |
| INTERSECT ALL / EXCEPT ALL | ✅ | ❌ | ❌ | ❌ |

> 注意！！！MySQL 不支持 INTERSECT 和 EXCEPT。要实现交集，用 `INNER JOIN` 或 `EXISTS`；要实现差集，用 `NOT EXISTS` 或 `LEFT JOIN ... WHERE IS NULL`。Oracle 的差集叫 `MINUS`，见到了认识就行。

---

## 十三、集合运算结果的列名和类型继承

- **列名**：由**第一个 SELECT** 决定。后面 SELECT 的列名会被忽略。
- **类型**：对应列取两个类型的**兼容类型**（比如 INT 和 BIGINT 会统一成 BIGINT）。

所以写集合运算时，把"你希望结果叫什么列名"放在第一个 SELECT 里起好别名。
